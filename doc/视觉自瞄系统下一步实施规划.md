# 视觉自瞄系统下一步实施规划

日期：2026-10-15  
状态：**规划稿，以下功能均不代表已实现或已接入运行主链。**

## 1. 规划依据与目标

当前工程已完成相机图像进入视觉线程、TensorRT 0526 四点 YOLO 检测、候选后处理及结果回传显示。`DetectedArmor` 是经过几何、身份和置信度校验的单帧二维观测；`vision_to` 当前传递原图、采集时间戳、装甲板列表和耗时。`ArmorRefiner`、`light_bar` 和 `light_result` 已保留实现，但没有接入 `trd_vision`。

下一阶段目标不是重做检测器，而是把“单帧二维装甲板”逐步扩展成**可评估的角点观测 → 相机坐标系三维位姿 → 跨帧稳定目标 → 只读瞄准建议**。优先复用当前数据契约和线程话题；参考项目 `temp/Dust_infantry_vision-main` 用于借鉴模块职责和验证顺序，不整套搬运其运行时、坐标系、通信或控制实现。

## 2. 当前基线与边界

- 已有：海康相机线程、`camera_to`/`vision_to` 单槽话题、`ArmorDetector`、`DetectedArmor`、检测统计和显示。
- 已有但未接入：`ArmorRefiner` 局部灯条提取及角点细化。
- 尚无：自动化视觉回放/评估基线、红蓝阵营策略与目标锁定切换、相机标定与 PnP、跨帧跟踪、目标预测、云台瞄准控制和开火控制。
- 当前 `vision_to` 的二维结果不应直接等同于“已确定世界坐标目标”或“可直接发射的控制量”。
- 置信度、角点误差、位姿误差是不同指标。蓝色样本的 objectness 高约 0.04，不能单凭窗口显示断定是亮度造成；应先按颜色、距离、曝光与目标类别分组统计并对照人工标注。

## 3. 推荐实施阶段

### P0：建立离线评估基线（优先做）

**目的：** 在继续叠加算法前确认当前模型到底错在哪里，并形成可复现回归集。

**涉及位置：** `framework/algorithm/vision/detect/armor_detector.*`、现有检测统计结构、显示/回放入口；评估工具和样本清单放在独立测试或工具目录，具体目录随仓库现有构建组织确定。

**工作内容：**
- 保存覆盖红/蓝、不同距离、运动模糊、亮暗曝光、遮挡和不同装甲类型的短视频/帧；保留原始图像、模型输出和运行配置版本。
- 为抽样帧人工标注四角点、颜色、类别与可见性，建立固定训练外评估集。
- 统计检测召回/误检、类别混淆、置信度分布、角点像素误差及处理耗时；红蓝对照要尽量匹配场景和曝光。
- 加入坐标还原、角点顺序、身份映射和 `DetectedArmor::Create` 边界条件的单元/离线回归检查；硬件依赖测试可标记为需 GPU/TensorRT。

**验收：** 同一版本可在固定数据集重复跑出相同检测记录；报告能区分检测漏失、身份错分和角点偏差；不以单个置信度数值当作几何精度。

### P1：增加 YAML 阵营过滤与目标颜色策略

**目的：** 明确哪些检测属于可攻击候选，避免把队友纳入锁定；在颜色策略明确后尽早丢弃不需要的候选，减少后续关联/选择工作。

**建议配置：** 在视觉线程自己的 YAML 中加入明确字段，例如 `own_color: red` 和 `target_color: enemy`。`own_color` 必须是 `red` 或 `blue`；`target_color` 可为 `enemy`、`red`、`blue` 或 `both`。配置解析应校验字段和值，缺失或非法时启动失败或安全地禁用目标输出，不得静默默认可攻击颜色。最终键名与配置文件位置在实现前按项目配置约定确定。

**安全语义：** `own_color` 是硬性排除条件，任何模式都不能把它作为自瞄锁定对象。`enemy` 表示自动选择与 `own_color` 相反的阵营；显式 `red`/`blue` 请求若与 `own_color` 相同，必须拒绝配置或进入只显示、不锁定状态。`both` 可用于红蓝检测/显示和数据采集，但在只有视觉颜色、没有可靠自方识别信息时，不能保证队友不被选中，因此默认只允许观测，不允许产生可执行锁定。若未来要让 `both` 可锁定，必须另有可靠友敌识别依据和单独安全评审。

**筛选位置：** 可在模型颜色类别已解码后尽早过滤非候选颜色，避免它们进入 NMS 后的类别/几何校验及后续跟踪选择；需同步保留过滤计数。注意这只能减少后处理候选，不能减少 YOLO 本身的 25200 行推理输出或 TensorRT 推理耗时。

**验收：** 对配置逐项测试；自方颜色在所有锁定路径都被排除；`enemy` 随 `own_color` 正确反转；`both` 模式虽可显示红蓝检测但锁定状态明确为禁用；过滤前后统计可核对，结果不发生颜色标签误映射。

### P2：评估并按需接入角点精修（条件阶段）

**目的：** 判断现有 `ArmorRefiner` 是否能修正影响后续几何解算的角点误差，而不是默认打开传统检测。

**涉及位置：** `framework/algorithm/vision/refine/armor_refiner.*`、`core/light_bar.*`、`core/light_result.hpp`，以及 `project/thread/vision/trd_vision.cpp` 的检测后处理位置；配置入口应沿用项目现有配置方式，不在本阶段顺手改其它运行参数。

**工作内容：**
- 先在 P0 标注集上离线比较 YOLO 原始角点与精修角点。
- 对照精修成功率、角点误差变化、失败原因和耗时；分颜色/曝光/距离看是否有系统性退化。
- 若接入，保持 YOLO 结果为基准；精修失败必须回退原四点，不能删除原本有效检测。保留可关闭开关，并能在调试输出中区分原始点与精修点。

**验收/停止条件：** 精修在代表性样本上可重复降低角点误差，且失败回退正确、耗时满足帧率预算，才进入主链；无稳定收益就保持未接入，不把“多了一套 OpenCV 处理”当成改进。

### P3：完成标定数据与单帧 PnP

**目的：** 把通过验证的四角点转换为相机坐标系下的装甲板姿态和距离。

**参考：** `temp/Dust_infantry_vision-main/tasks/auto_aim/solver.*` 的职责划分与重投影检查。仅借鉴“输入二维角点、物理模型和相机参数，输出位姿及质量信息”的接口思路。

**前置事项：**
- 采集并校验当前相机内参、畸变参数；明确图像旋转/翻转后的坐标约定。
- 明确小/大装甲板的真实物理尺寸、物点顺序与 YOLO 四角点顺序的一一对应。
- 相机到云台/车体的外参单独标定；记录坐标系方向、单位、旋转表示法及标定来源，禁止凭参考项目参数填值。

**涉及位置：** 现有 `DetectedArmor` 和 `vision_to` 作为输入边界；新增位姿求解模块建议放入 `framework/algorithm/vision` 的独立子层，配置沿用本项目配置体系。是否扩展 `vision_to` 或建立后续话题，在设计阶段核对订阅者后再定。

**验收：** 用已知距离/姿态的静态样本验证重投影误差与距离误差；覆盖两种装甲尺寸、画面边缘、倾斜视角和无效角点；解算失败显式标记，不输出看似有效的默认位姿。

### P4：实现跨帧目标关联、锁定与切换

**目的：** 在连续帧中维持目标身份和短时丢失状态，提供稳定观测；允许上层通过明确输入锁定、切换目标，而不是每帧独立选最高置信度框。

**参考：** `tasks/auto_aim/tracker.*`、`target.*` 的检测关联和生命周期拆分。参考其状态机思想，不照搬其 EKF 状态、噪声参数或装甲关联门限。

**涉及位置：** 新增跟踪/目标状态模块；由视觉线程按帧时间戳调用，并通过明确的话题或结果结构向下游发布。保留现有 `DetectedArmor` 作为每帧观测，不把滤波状态塞进检测对象。锁定/切换命令应经线程安全的命令或话题接口传递，不直接跨线程改写跟踪器内部状态。

**工作内容：** 只从 P1 允许锁定的颜色候选中建立目标；先做单目标、可解释的关联规则（颜色/类别约束、中心或角点距离门限、时间连续性），定义 `unlocked`、`tracking`、`temporarily_lost`、`lost` 等状态。锁定应有稳定身份键（如阵营、标签、尺寸及空间/图像关联，不仅按置信度）；切换请求在当前候选无效、颜色策略不允许或目标过期时应明确失败并解除旧锁，不能悄悄留用旧目标。再用回放数据调参。滤波器和动态 ROI 是后续优化，不是第一版前置条件。

**验收：** 回放中目标 ID 不因轻微检测抖动频繁跳变；切换命令只在允许颜色集合内生效；队友永不成为锁定目标；短暂遮挡按配置进入暂失并按时退出；长时间丢失后不沿用过期目标发出有效跟踪结果；时间戳和帧序可追溯。

### P5：输出只读瞄准建议（不接真实执行）

**目的：** 将目标位姿与云台反馈转换为可观测、可验证的 yaw/pitch 建议，先验证坐标、延迟和预测误差。

**参考：** `tasks/auto_aim/planner/` 和 `io/talos/` 的职责划分；不直接移植 TinyMPC，也不把 Talos 当作当前工程已有后端。

**工作内容：** 接入真实采集时间戳对应的云台反馈，定义清晰的相机、云台、车体坐标变换；先输出日志/可视化建议值，不下发控制。比较静止目标、运动目标和不同延迟下的角度误差，再决定是否需要预测器或 MPC。

**验收：** 已知方向目标的 yaw/pitch 符号正确；反馈超时、位姿无效、跟踪丢失或计算超时时输出“无有效建议”；建议值可由离线回放复现。真实云台命令和开火控制不属于本阶段。

## 4. 后续阶段与安全门禁

真实云台控制需要独立完成硬件协议、限幅、急停、反馈超时和通信故障验证；自动开火还需要独立授权与安全测试。它们必须在 P0–P5 结果经实机/仿真验证后另立规划，默认保持关闭，不以参考项目中存在相关模块作为接入依据。

## 5. 参考项目取舍

| 参考模块 | 适合借鉴 | 暂不照搬 |
| --- | --- | --- |
| `solver.*` | PnP 输入输出职责、重投影验证思路 | 未经本机标定的内外参、物点和坐标约定 |
| `tracker.*` / `target.*` | 目标生命周期、检测关联与状态拆分 | 未经数据验证的 EKF 状态维数、噪声和关联阈值 |
| `planner/` | 将目标状态与云台反馈解耦的边界 | 直接接入 TinyMPC、控制输出和开火逻辑 |
| `dynamic_roi.*` | 稳定跟踪后作为推理优化的候选 | 跟踪未稳定前缩小视野，导致漏检后无法恢复 |
| `io/talos/` | 仿真 I/O 与算法隔离的架构参考 | 假设当前工程已有 Talos 接口或可直接复用其消息 |

不建议下一步做的事：重写 YOLO 后处理、重建已删除的全图灯条配对路线、先搬整套参考项目、先做动态 ROI/MPC/多线程推理，或仅为红蓝置信度差异手工加类别偏置。

## 6. 建议执行顺序与每步交付

```text
P0 离线数据与指标基线
  → P1 YAML 阵营过滤与目标颜色策略
  → P2 仅在角点确有收益时接入精修
  → P3 标定与单帧 PnP
  → P4 跨帧关联、锁定与切换
  → P5 只读瞄准建议
  → 另行评审真实控制与开火
```

每阶段合并前都应提供：改动文件清单、配置/坐标契约说明、可重复的验证数据或命令、通过与失败统计、未解决风险。若阶段验收不通过，停在该阶段修正，不把问题带入下游滤波或控制。

## 7. 完成定义

这份文档只定义后续实施顺序，不代表任何 P0–P5 功能已经开发。建议先完成 P0 小规模可复现数据集和角点评估工具，再实现 P1 阵营过滤策略；之后根据评估结果决定是否接回精修，而不是立刻搬入参考项目的 Tracker 或 Planner。
