# 局域网远程控制软件可行性与实现规划

## 1. 文档目标与范围

本文档规划一个独立的个人局域网远程控制软件，与当前 OpenCV 视觉项目无关。目标是让一台控制端电脑实时观看同一局域网内受控端的屏幕，并用本地鼠标和键盘操作它。音频共享、文件传输和多端观看属于后续扩展。

本规划优先考虑 Linux 桌面系统与现代 C++ 实现，但整体架构不绑定特定平台。第一版就覆盖“受控端采集并发送屏幕，控制端显示画面并回传鼠标键盘事件，受控端注入输入”这条完整闭环。

## 2. 可行性结论

在同一局域网中实现屏幕共享完全可行，而且相比公网远程桌面更容易做到低延迟、高画质和稳定传输。局域网内通常不需要 NAT 穿透、公网中继服务器和复杂的连接保活，核心难点集中在以下几件事：

- 如何高效采集屏幕，尽量减少数据拷贝。
- 如何使用 H.264、H.265 或 AV1 等编码降低带宽。
- 如何在丢包、抖动和带宽变化时保持画面连续。
- 如何在高分辨率与低延迟之间取得平衡。
- 如何处理 Linux 下 X11 与 Wayland 不同的屏幕采集和输入注入接口。

在同一局域网内做个人自用的一对一远程控制，不需要公网穿透、云端账号、中继服务器和企业级权限系统，实现难度可控。主要难点是屏幕延迟、坐标映射、组合键状态和 Wayland 下受桌面系统管理的远程输入接口。

## 3. 需求分层

为了符合“自己方便使用”的目标，功能优先级调整如下。

### 3.1 核心闭环：画面与键鼠控制

受控端分享整个桌面，控制端显示画面，并回传鼠标移动、按键、滚轮和键盘按下/抬起事件。这是本项目的最小可行产品（MVP）。

### 3.2 使用体验：剪贴板、快捷键与系统音频

在基本控制成功后，再增加文本剪贴板同步、特殊组合键、系统音频和显示质量档位。这些功能会明显提升日常使用体验，但不应阻塞键鼠控制闭环。

### 3.3 后续扩展：多平台、多屏和多接收端

第一版只支持两台 Linux 电脑之间一对一控制。Windows、macOS、多显示器快速切换和多个观看者等功能延后。

## 4. 整体数据链路

```text
用户选择屏幕/窗口
        ↓
屏幕采集 → 色彩/尺寸转换 → 视频编码 → 分包与加密
                                                     ↓
                                               局域网传输
                                                     ↓
窗口渲染 ← 色彩转换/缩放 ← 视频解码 ← 抖动缓冲与重组
```

会话控制链路与视频链路分开：

```text
填写 IP/设备发现 → 连接请求 → 能力协商 → 开始/停止/参数调整
```

远程输入是第三条反向链路：

```text
控制端窗口获取鼠标/键盘事件
        ↓
坐标变换与按键标准化 → 可靠数据通道 → 受控端输入状态机
                                                        ↓
                                           XTest 或 Portal + libei
```

三条链路分开的好处是：画面即使丢包，也不应导致键盘按下/抬起、鼠标按键、停止控制或会话状态丢失。鼠标移动事件可以合并或丢弃过时值，但键盘和鼠标按键事件必须按序可靠到达。

## 5. 关键子系统设计

### 5.1 屏幕采集

Linux 需要分别考虑 X11 和 Wayland：

- X11 可以通过 XShm、XComposite 或 FFmpeg/GStreamer 的现成采集源实现，权限相对宽松。
- Wayland 不允许普通应用程序随意读取其他窗口。正常路径是调用 `xdg-desktop-portal` 的 ScreenCast 接口，由用户明确选择屏幕或窗口，然后通过 PipeWire 获取视频流。
- 对第一版建议直接把 PipeWire + ScreenCast Portal 作为 Linux 主路径，不尝试绕过桌面系统的权限确认。
- 采集层只输出统一的 `VideoFrame`，不应让编码层直接依赖 PipeWire 或 X11 类型。

建议的帧对象至少包含：

- 宽度、高度和像素格式。
- 采集时间戳和递增帧号。
- CPU 内存或 GPU/DMABUF 缓冲区句柄。
- 光标是否已烧录在图像中。
- 屏幕旋转、缩放比和颜色空间等元数据。

### 5.2 编码

原始屏幕数据量很大。以 1920×1080、BGRA、60 帧每秒为例，未压缩数据约为 475 MiB/s，普通千兆局域网也无法直接承载，因此必须编码。

| 编码 | 优点 | 不足 | 建议 |
| --- | --- | --- | --- |
| H.264 | 支持广、硬件编解码普及、低延迟参数成熟 | 同画质压缩率低于新编码 | MVP 首选 |
| H.265/HEVC | 同画质下通常更省带宽 | 软件、授权与浏览器支持需单独核对 | 作为后续可选项 |
| AV1 | 压缩效率高，开放生态好 | 软编码成本高，老设备硬件支持不统一 | 不作为第一版默认 |
| MJPEG | 实现和调试简单，每帧独立 | 带宽大，高分辨率时不划算 | 只用于早期链路验证 |

MVP 建议使用 H.264，并明确使用低延迟配置：

- 尽量不使用 B 帧。
- 限制编码器内部缓冲，避免帧在队列中堆积。
- 按需请求关键帧，用于接收端加入或丢包后恢复。
- 对桌面文字保留足够码率，不只用“视频看起来还行”作为画质标准。
- 先实现软件编码保证功能闭环，再增加 VA-API、NVENC 等硬件后端，避免第一步就被显卡驱动差异卡住。

### 5.3 传输

屏幕视频对传输的要求不是“每个包必须到达”，而是“最新画面尽快到达”。如果直接使用普通 TCP 并无限堆积待发数据，网络一旦波动，用户看到的就会是几秒前的完整画面。

可选方案对比：

| 方案 | 适合场景 | 优点 | 主要代价 |
| --- | --- | --- | --- |
| WebRTC | 正式版、浏览器接收、后续跨平台 | 自带加密、实时传输、拥塞控制、网络反馈和数据通道 | 需要 SDP/ICE 信令交换，原生 C++ 接入复杂度较高 |
| RTP/UDP + RTCP | 学习原理、纯局域网原型 | 数据路径直接，延迟可控 | 加密、丢包恢复、拥塞控制和会话管理要自己补齐 |
| SRT | 稳定推流、一定弱网对抗 | 成熟、可配延迟、有重传机制 | 桌面交互生态和浏览器集成不如 WebRTC |
| 自定义 TCP | 功能验证 | 容易编写和调试 | 队头阻塞明显，不适合作为最终实时方案 |

推荐把 WebRTC 作为正式路线。即使只在局域网中使用，WebRTC 仍能提供成熟的实时媒体传输、加密和网络适应。但 WebRTC 本身不定义信令服务，软件仍需要一条 WebSocket 或 HTTP 控制连接交换 offer、answer 和 ICE candidate。

如果目标首先是学习视频分包与传输原理，可先用 GStreamer 快速搭出 RTP/UDP 原型，完成测量后再转向 WebRTC。这个 RTP 原型是验证工具，不是最终产品架构。

### 5.4 设备发现与建立会话

建议分两步实现：

1. MVP 阶段由控制端输入受控端 IP 和端口，消除自动发现对核心闭环的干扰。
2. 工程化阶段使用 mDNS/DNS-SD 发布服务，在 UI 中列出同网段可用设备，同时保留 IP 直连作为备用。

个人自用版的连接流程可以很简单：

1. 控制端输入受控端 IP 和端口。
2. 受控端默认接受局域网连接；如果日后有需要，再增加可选确认开关。
3. 协商编码、分辨率、帧率、码率上限和键鼠能力。
4. 建立视频通道和输入数据通道，进入控制状态。
5. 任一方停止后，先释放所有按下的键鼠状态，再释放采集、编码和网络会话。

### 5.5 接收、解码与显示

接收端不应为了“不丢帧”无限增大缓冲。对屏幕共享而言，过时帧没有价值。

建议策略：

- 抖动缓冲先从 30–80 ms 小范围起步，再根据实测调整。
- 解码或渲染来不及时丢弃旧帧，优先显示最新帧。
- 网络丢包破坏参考链时请求新关键帧，不长时间显示花屏。
- 渲染层保持等比缩放，黑边与裁剪策略由用户选择。
- 全屏、窗口化和多显示器布局不应反向影响解码层。

### 5.6 远程鼠标与键盘

远程输入不应传输 Qt、SDL 或 X11 的原始事件结构体，而应定义平台无关的输入消息：

```text
PointerMoveRelative { dx, dy }
PointerMoveAbsolute { normalized_x, normalized_y, display_id }
PointerButton       { button, pressed }
PointerScroll       { horizontal, vertical }
KeyboardKey         { physical_code, logical_symbol, pressed, modifiers }
ReleaseAllInputs    { reason }
```

建议把输入事件放在 WebRTC DataChannel 上。对于键盘按键、鼠标按键、滚轮和剪贴板，使用有序可靠通道；高频鼠标移动可以在后续优化为只保留最新值，避免卡顿后重放一长串过时轨迹。

Linux 受控端有两条实现路线：

- X11：通过 XTest 扩展生成鼠标移动、鼠标按键和键盘事件。这条路径简单，适合先快速打通键鼠闭环。
- Wayland：使用 XDG RemoteDesktop Portal 建立远程桌面会话，将同一会话与 ScreenCast 结合。输入注入优先调用 `ConnectToEIS()` 获取文件描述符，再通过 libei 发送指针和键盘事件。

因为目标是个人自用，可以先选定一个实际桌面环境完成。如果当前两台电脑都运行 X11，先做 XTest 是最快路线；如果日常环境是 Wayland，就应直接做 Portal + libei，避免先写一套日常无法使用的 X11 后端。

坐标映射是远程控制最容易出错的地方：

1. 控制端先把鼠标从窗口坐标换算到实际画面内容坐标，排除黑边和 UI 工具栏。
2. 将画面坐标归一化为 `[0, 1]`，传输显示器 ID 和归一化坐标。
3. 受控端根据当前显示器几何、DPI 缩放和旋转恢复为桌面逻辑坐标。
4. 屏幕分辨率或布局改变后，受控端必须立即更新几何信息，不继续使用旧坐标映射。

键盘处理需同时保留“物理键位”和“逻辑字符”的概念。例如 `Ctrl+C`、`Alt+Tab` 更适合物理键位，文字输入则涉及受控端键盘布局和输入法。MVP 先保证常用按键、组合键和英文输入；中文输入可以先通过剪贴板同步解决，之后再完善输入法适配。

无论使用哪种平台后端，只要发生断网、窗口失去焦点、控制模式关闭或会话结束，都必须在受控端执行 `ReleaseAllInputs`，防止 `Ctrl`、`Alt` 或鼠标键留在按下状态。

## 6. 推荐架构

这应是一个新的独立工程，不放入当前视觉项目的 `framework` 或 `project/thread` 中。建议按如下职责分层：

```text
lan-remote-control/
├── app/
│   ├── host/                # 受控端入口与状态 UI
│   └── controller/          # 控制端入口、画面和输入 UI
├── core/
│   ├── capture/             # 统一采集接口与平台后端
│   ├── codec/               # 编码、解码和能力探测
│   ├── media/               # 帧、包、时间戳和缓冲管理
│   ├── transport/           # WebRTC/RTP 传输适配
│   ├── signaling/           # 会话建立和控制消息
│   ├── input/               # 输入协议、坐标映射和按键状态机
│   ├── discovery/           # IP 直连与 mDNS
│   ├── session/             # 连接、控制启停和会话状态
│   └── stats/               # 延迟、码率、丢包和帧率统计
├── platform/
│   ├── linux/               # PipeWire/Portal、X11 可选后端
│   ├── windows/             # 后续 Desktop Duplication API
│   └── macos/               # 后续 ScreenCaptureKit
├── tests/
│   ├── unit/
│   ├── integration/
│   └── network/
└── docs/
```

核心接口可以围绕以下概念设计：

```cpp
class IScreenCapture;
class IVideoEncoder;
class IVideoDecoder;
class IMediaTransport;
class ISignalingChannel;
class IVideoRenderer;
class IInputCapture;
class IInputInjector;
```

这些接口的价值是隔离平台差异和第三方库，不是为了在第一版做出很多“空抽象”。每个接口应至少有一个实际后端后再固化。

## 7. 技术栈建议

### 7.1 原型路线

- 语言：C++17 或 C++20。
- 快速媒体链路：GStreamer。
- Linux 采集：xdg-desktop-portal + PipeWire。
- 视频编码：H.264 软件编码起步。
- 显示：SDL2/SDL3 或 Qt，二选一。
- 传输：先用 RTP/UDP 做链路原型，只用于单机和可控局域网调试。
- 输入回传：原型可先用同一条 TCP/WebSocket 控制连接，受控端根据实际桌面选择 XTest 或 Portal + libei。

### 7.2 正式路线

- UI：Qt，负责设备列表、授权弹窗、画质设置和统计界面。
- 媒体：GStreamer 继续承担采集、颜色转换、编解码管线，或在边界稳定后局部替换为 FFmpeg/原生平台 API。
- 传输：WebRTC，可使用 GStreamer `webrtcbin` 或选定的原生 WebRTC 库。
- 键鼠通道：WebRTC DataChannel，与视频流使用同一会话。
- Wayland 输入注入：XDG RemoteDesktop Portal + libei；X11 输入注入：XTest。
- 信令：WebSocket，一开始可由受控端在局域网监听，不需要外部云服务器。
- 设备发现：mDNS/DNS-SD。
- 序列化：控制消息优先使用简单、可读的 JSON；数据量明显增大后再考虑 Protobuf。

OpenCV 不是这个软件的必需依赖。它可用于调试时显示帧、画时间戳或进行像素转换，但不宜承担实时媒体传输主体。

## 8. 性能目标与预算

第一版应先定义可测量指标，而不是只验收“能看到画面”。

### 8.1 建议默认参数

- 分辨率：1920×1080。
- 帧率：30 FPS，后续增加 60 FPS 档位。
- 编码：H.264。
- 码率起点：6–10 Mbit/s，再根据文字清晰度和网络状态调整。
- 端到端延迟：有线局域网争取低于 100 ms，首版验收上限可设为 150 ms。
- 操作响应：从控制端发生输入到新画面显示操作结果，首版争取低于 200 ms。
- 无限压队列：禁止；采集到编码的待处理帧最多保留 1–2 帧。

上述码率只是工程起点，不是固定结论。静态代码页面、视频播放、游戏画面和频繁滚动的桌面对码率需求差异很大，必须通过场景化测试确定。

### 8.2 延迟预算

| 环节 | 首版参考预算 |
| --- | --- |
| 等待下一帧采集 | 0–33 ms（30 FPS） |
| 颜色转换与缩放 | 2–10 ms |
| 编码 | 5–30 ms，取决于软硬件和配置 |
| 局域网传输 | 通常为数毫秒，但 Wi-Fi 抖动可明显增大 |
| 抖动缓冲 | 30–80 ms |
| 解码与显示 | 5–30 ms |

延迟优化的优先级应是：先消除队列堆积，再收紧编解码缓冲，最后才做零拷贝和 GPU 管线。

## 9. 线程与缓冲模型

受控端可以采用以下执行单元：

1. UI/主线程：处理用户选择和连接确认。
2. 采集回调或采集线程：获得最新帧。
3. 编码执行单元：消费最新帧并产生编码包。
4. 网络事件循环：处理信令、媒体传输和反馈。
5. 输入注入执行单元：按序处理控制端键鼠事件，并维护按下状态集合。

控制端可以采用：

1. 网络事件循环：收包和重组。
2. 解码执行单元：输出可显示帧。
3. UI/渲染线程：显示最新帧和统计信息。
4. 输入采集：将视频窗口中的键鼠事件标准化后发往受控端。

并发设计的核心规则：

- 队列必须有上限。
- 最新帧优先于旧帧。
- 网络变慢时优先降低码率、帧率或分辨率，不是继续积压。
- 停止时有明确的状态机，不依赖线程被强制终止。
- 帧和编码包尽量使用引用计数或缓冲池，但先保证所有权正确，再优化拷贝。

## 10. 个人使用下的最小连接边界

本项目仅供个人在自己的局域网和设备之间使用，因此不规划账号体系、企业权限、设备审计、云端密钥管理或复杂信任链。只保留不影响开发进度的最低运行边界。

最低要求：

- 可以直接填写受控端 IP 连接，不强制做账号登录和配对。
- 受控端显示“正在被控制”状态，并提供本地一键停止。
- 程序只在选定的局域网网卡上监听，不主动暴露到公网。
- 优先使用 WebRTC 已有的加密传输，不额外自己设计加密协议。
- 不以 root 身份运行整个应用；Wayland 下使用桌面 Portal 正常授予的输入权限。
- 断网、停止控制和程序退出时必须释放所有键鼠按下状态。

## 11. 开发阶段规划

### 阶段 0：画面与输入技术验证

目标：不写完整 GUI，先证明当前电脑的采集、编解码、网络和输入注入都可用。

工作内容：

- 确认桌面会话是 X11 还是 Wayland。
- 用 PipeWire/Portal 或 GStreamer 成功采集屏幕。
- 完成本机“采集 → H.264 编码 → 解码 → 显示”。
- 在两台局域网设备之间完成临时 RTP/UDP 传输。
- 根据实际桌面选定 XTest 或 Portal + libei 后端。
- 在受控端本机测试鼠标移动、左右键、滚轮、字母键和 `Ctrl+C/Ctrl+V`。
- 记录 CPU/GPU 占用、码率、帧率与端到端延迟。

验收：1080p30 连续运行 30 分钟，没有无界队列增长、持续性花屏或数秒级延迟；本机输入注入后端可正确操作常规桌面应用。

### 阶段 1：局域网远程控制 MVP

目标：形成可独立启动的受控端和控制端，完成“看得到、点得到、输入得了”的完整闭环。

工作内容：

- 分享整个主屏幕。
- IP 和端口直连。
- H.264 软件编解码。
- 有界帧队列与丢帧策略。
- 定义输入消息，先用 TCP 或 WebSocket 可靠回传。
- 完成鼠标绝对坐标、左右键、滚轮、常用键盘按键与组合键。
- 完成窗口黑边、画面缩放和受控端 DPI 的坐标映射。
- 断网、失去焦点和退出时执行 `ReleaseAllInputs`。
- 显示 FPS、码率、丢包率、往返时延和估算端到端延迟。
- 任一端都可以随时停止控制。

验收：有线局域网 1080p30 稳定运行，端到端画面延迟不高于 150 ms；能用控制端打开菜单、拖动窗口、滚动页面、在文本编辑器输入英文并执行常用组合键；异常断开后没有键或鼠标按钮卡住。

### 阶段 2：WebRTC 与工程化

目标：用 WebRTC 替换临时传输，建立可长期演进的会话模型。

工作内容：

- WebSocket 信令通道。
- SDP/ICE 能力协商。
- WebRTC 加密媒体传输。
- 将键鼠从临时 TCP/WebSocket 通道迁移到 WebRTC DataChannel。
- 网络反馈、动态码率和关键帧请求。
- 会话状态机：空闲、连接、协商、控制、断线、停止。
- 自动重连，重连后重建输入状态，不重放旧的键鼠事件。

验收：在可控丢包、限带和抖动条件下，画面能降级而不是无限增加延迟，网络恢复后能自行回到正常状态。

### 阶段 3：性能与体验

目标：从“可用”进入“好用”。

工作内容：

- VA-API/NVENC 等硬件编码后端。
- 硬件解码。
- DMABUF/GPU 零拷贝路径，需以实测收益决定是否启用。
- 1080p60 模式。
- 自动发现和已保存受控端列表。
- 剪贴板、系统音频和多显示器。
- 完善日志、故障诊断和崩溃恢复。

验收：硬件编码对 CPU 占用有可量化的改善，且不以额外数帧缓冲换取低 CPU。

### 阶段 4：日常使用扩展

基础键鼠控制已在 MVP 完成，这一阶段补齐长期使用时有价值的功能。

可选内容：

- 中文剪贴板同步和文件拖放。
- 系统音频回传。
- 多显示器列表、单屏切换和整个虚拟桌面模式。
- 受控端开机自启、固定端口和记住上次控制端。
- 自动发现受控端，免去每次输入 IP。
- 按需增加 Windows 或 macOS 平台后端。

## 12. 测试规划

### 12.1 功能测试

- 整屏、单窗口和多显示器选择。
- 分辨率改变、屏幕旋转、窗口最小化和显示器热插拔。
- 控制端中途加入、退出和再次连接。
- 受控端主动停止和程序异常退出。
- 鼠标移动、单击、双击、拖拽、左右键和滚轮。
- 普通键、长按、组合键、大小写和功能键。
- 视频窗口带黑边、拉伸和全屏时的坐标映射。
- 断网、控制端崩溃或窗口失焦后，受控端没有按键卡住。

### 12.2 网络测试

- 有线千兆局域网。
- 5 GHz/6 GHz Wi-Fi。
- 2.4 GHz Wi-Fi 和信号较差的场景。
- 1%、5%与 10% 丢包。
- 上下行限带、延迟突增和抖动。
- 网卡切换、IP 变更和短暂断网。

### 12.3 场景画面测试

- 静态文本和代码：检查小字清晰度。
- 页面快速滚动：检查拖影和码率适应。
- 全屏视频：检查连续运动画面。
- 游戏或 3D 画面：检查高变化量时的画质和延迟。
- 几乎静止的桌面：检查码率能否合理下降。

### 12.4 延迟测量

只看日志中的网络 RTT 不能代表屏幕端到端延迟。建议同时采用：

- 帧内嵌入采集时间戳，在同步时钟的两台设备上统计。
- 高帧率相机同时拍摄受控端上的计时画面和控制端显示画面，获得更接近用户感知的延迟。
- 对采集、进编码器、出编码器、收包、出解码器和实际渲染分别打点，定位延迟所在环节。
- 额外测量“控制端产生输入 → 受控端注入 → 新画面被采集 → 控制端显示”的操作闭环延迟。

## 13. 主要风险与应对

| 风险 | 典型现象 | 应对方式 |
| --- | --- | --- |
| Wayland 权限与桌面差异 | 无法直接抓屏或注入键鼠、出现系统授权弹窗 | 使用 RemoteDesktop Portal 同时管理 ScreenCast 和 libei，在实际桌面环境验证 |
| CPU 占用过高 | 1080p60 时卡顿、风扇高转 | 先检查颜色转换和多次拷贝，再引入硬件编码和零拷贝 |
| 延迟越来越大 | 画面完整但落后几秒 | 所有队列有界，丢旧帧，启用码率自适应 |
| 文字发糊 | 视频可看但 IDE 字体难辨认 | 增加码率，调整色度格式，增加桌面内容专用档位 |
| Wi-Fi 抖动 | 间歇性卡顿或花屏 | 使用 WebRTC 反馈、可变码率、关键帧恢复和有限抖动缓冲 |
| 鼠标坐标偏移 | 点击位置与画面不一致 | 归一化画面坐标，明确处理黑边、DPI、旋转和多显示器几何 |
| 按键卡住 | 断网后 `Ctrl` 或鼠标按键仍为按下 | 受控端记录按下集合，所有退出路径统一执行 `ReleaseAllInputs` |
| 平台抽象过早 | 写了很多接口但 Linux 闭环仍未跑通 | 先完成一个 Linux 后端，再根据真实差异抽象 |
| 把原型当产品 | UDP 演示能跑，但没有加密、授权和弱网能力 | 在文档和代码中标明 prototype 边界，阶段 2 替换传输层 |

## 14. 一对多共享的扩展思路

第一版只做一对一。对于多接收端，有三种路线：

1. 发送端对每个接收端各发一路。实现最简单，但上行带宽随观看者数量线性增长。
2. 发送端只编码一次，对多个会话复用编码流。可减少编码开销，但不同接收端的带宽适应会受限。
3. 在局域网部署 SFU，发送端只上传一次，由 SFU 转发给多个观看者。适合较多观看者，但引入了额外服务端。

如果目标是教室广播或实验室演示，应在完成一对一后直接评估 SFU，不要默认让发送端为几十个观看者重复发流。

## 15. 建议的第一个实现版本

为了快速进入真实闭环，推荐第一个版本严格限定为：

- 两台 Linux 电脑。
- 同一局域网，优先有线。
- 受控端分享一个完整主屏幕。
- 控制端可使用鼠标、滚轮、常用键盘按键和组合键。
- 暂无音频、无文件传输；中文可先用剪贴板同步扩展解决。
- 1080p30、H.264。
- 手动输入 IP 连接。
- 屏幕采集使用 Portal + PipeWire。
- 输入注入根据当前桌面使用 XTest 或 Portal + libei。
- 传输最终目标为 WebRTC；允许先用 RTP/UDP 完成阶段 0 验证。

这个版本成功后，再按“WebRTC DataChannel 整合 → 硬件编码 → 自动发现 → 剪贴板/音频 → 多屏 → 跨平台”的顺序逐项扩展。

## 16. 不建议的做法

- 不传输未压缩原始帧。
- 不用无界 TCP 发送队列保证“一帧不丢”。
- 不在第一版同时支持 Linux、Windows、macOS、Android 和浏览器。
- 不为了避免授权弹窗而绕过 Wayland Portal 权限模型。
- 不把发现局域网设备等同于授权它观看屏幕。
- 不先写一套自定义视频编码或完整实时传输协议。
- 不用“本机能显示”代替两台真实设备的局域网验收。

## 17. 最终判断

这个项目从技术上没有原理性障碍，并且很适合作为一个涉及 Linux 桌面、多媒体、网络、输入系统、并发和工程化的综合项目。对个人局域网自用场景，可以直接把远程键鼠纳入第一个 MVP，不需要先做一个只能观看的完整产品版本。

一句话概括推荐方案：

> Linux 上用 Portal + PipeWire 采集屏幕，用 H.264 做低延迟编码，用 WebRTC 传输视频和键鼠消息，受控端用 XTest 或 Portal + libei 注入输入，第一个 MVP 就完成一对一远程控制。
