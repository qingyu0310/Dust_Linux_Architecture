# 视觉算法目录分层规划

日期：2026-10-14。

对象：`framework/algorithm/vision/` 的目录结构与依赖方向。

状态：**规划，尚未动手。**

## 1. 目标与判据

现在的判据不是"看着舒服"，而是三条可检查的：

1. **一个文件一件事**：每个头文件里只放同一层的类型与接口，顶层声明数控制在个位数；
2. **依赖单向**：`图像/契约 → 具体检测器 → 精修器`，不许出现反向或横跨的 include；
3. **数据流一眼可见**：看目录名就知道"图进来、灯条出去、四点出去"。

## 2. 现状：实测

```
文件                     行数    顶层类型/类数   职责
armor.hpp                 708        14 ✗       5 件不相干的事混在一起
armor.cpp                 509         —         灯条 + 几何配对 + 模型解码 + DetectedArmor
light_detector.hpp/.cpp   194/308     5 ✓       传统提灯条（自洽）
armor_detector.hpp/.cpp   139/725     3 ✓       TensorRT 检测（自洽，单文件偏大）
armor_refiner.hpp/.cpp    132/338     3 ✓       四点精修（自洽）
                         ------
                          3053
```

`armor.hpp` 里的 14 个声明实际是 **5 类**东西：

| 类 | 声明 | 归谁 |
| --- | --- | --- |
| 队伍/尺寸/标签枚举 | `TeamColor` `ArmorSize` `ArmorLabel` | 全流程共用 |
| 检测结果契约 | `DetectedArmorGeometry` `DetectedArmorIdentity` `DetectedArmor` | 检测输出 / 跟踪输入 |
| 灯条几何 | `LightBarGeometry` `LightBar` | 图像层基础类型 |
| 几何配对 | `ArmorMetrics` `ArmorCandidate` `PairRejectReason` `PairResult` `ArmorGeometry` | 纯几何算法 |
| （cpp 里）模型类别解码 | `DecodeArmorModelColor/Label/Size`、`IsArmorLabelCompatibleWithSize` | 0526 模型专属约定 |

**依赖边**（实测 7 条 include，其中 3 条是跨层）：

| 谁 | 依赖 | 问题 |
| --- | --- | --- |
| `light_detector.hpp` | `armor.hpp` | 只为 `LightBar`，却被整份 708 行拖着 |
| `armor_detector.hpp` | `armor.hpp` | 同上（要 `TeamColor`/`ArmorLabel`/`DetectedArmor`） |
| **`armor_refiner.hpp`** | **`light_detector.hpp`** | **横跨**：只为 `LightDetectionStats`、`LightRejection` 两个结果类型，把整个检测器（含实现）拉进来 ✗ |
| 各 `.cpp` | 自己的 `.hpp` | 正常 |

## 3. 病灶

- **① `armor.hpp` 是垃圾桶**：14 个顶层声明里，"模型类别解码"的**约定**（0=蓝/1=红、7 和 8 都是基地）是模型专属知识，却和通用几何类型住在一个文件里；换模型要动的文件 = 通用类型文件 ✗。*怎么得出的：把 14 个声明按"谁会用"归类，落在 5 个不同层。*
- **② 结果契约长在检测器身上**：`LightDetectionStats`/`LightRejection`/`LightDetectionResult` 是**层间契约**（精修器也要用），却定义在 `light_detector.hpp` 里，逼得 `refine` 依赖 `detect` ✗。*怎么得出的：`armor_refiner.hpp:14` 的 include 边。*
- **③ 没有依赖规则可讲**：现在 8 个文件平铺，新加文件时"该 include 谁"没有约束，所以每次都要重新想一遍 ✗。*怎么得出的：目录下只有平铺的 8 个文件，没有子目录。*

## 4. 目标结构

```
framework/algorithm/vision/
├── core/                        契约与几何：不依赖任何检测器（只 OpenCV core + STL）
│   ├── armor_types.hpp          TeamColor / ArmorSize / ArmorLabel
│   ├── light_bar.hpp/.cpp       LightBarGeometry / LightBar
│   ├── light_result.hpp         LightRejectReason / Stats / Rejection / Result
│   ├── detections.hpp           DetectedArmorGeometry / Identity / DetectedArmor
│   └── armor_board.hpp/.cpp     ArmorMetrics / ArmorCandidate / PairRejectReason / PairResult / ArmorGeometry
├── detect/                      图像 → 目标（两条并列路径，互不依赖）
│   ├── light_detector.hpp/.cpp  传统：灰度二值化 + 外轮廓 + 几何/颜色门限
│   ├── model_decode.hpp/.cpp    0526 类别解码（含标签与尺寸自洽规则）
│   └── armor_detector.hpp/.cpp  TensorRT 推理 + 解码 + NMS
└── refine/                      粗四点 → 精确四点
    └── armor_refiner.hpp/.cpp   ROI 内找最近两根灯条
```

**依赖规则（唯一一条）：**

```
refine ─┐
        ├─→ core        （只此一个方向）
detect ─┘
```

- `core/` 不许 include `detect/`、`refine/`；
- `detect/` 与 `refine/` 之间**不许互相 include**（精修器用它自己的灯条提取，不再借检测器的结果类型）；
- 每个头文件自己 include 自己需要的依赖，不靠别的头顺带带进来。

**明确不改的**：namespace 一律保持 `algorithm::vision`（层次由目录 + 上面这条规则表达；改 namespace 会牵动所有调用点，只是噪音）。类名、函数签名、算法一概不动。

## 5. 分步骤

每一步都要能单独编译通过，做法是"搬 + 删 + 改所有引用者"一次做完。

### 步骤 1：把共用枚举拆成 `core/armor_types.hpp`

- **做什么**：`TeamColor` / `ArmorSize` / `ArmorLabel` 三个枚举搬过去，`armor.hpp` 里删掉、改成 include 新头。
- **落点**：新文件 `core/armor_types.hpp`；引用者 `armor.hpp`、`armor_detector.hpp`、`model_decode.cpp`（步骤 5 才建）。
- **验收**：`grep -rn "armor.hpp" framework/algorithm/vision | wc -l` 不变（引用还在，只是搬运）；编译 0 错误。
- **失败分叉**：若出现"枚举重复定义"→ 说明旧定义没删干净，删掉 `armor.hpp` 里的那份。

### 步骤 2：`core/light_result.hpp`，切断 `refine → detect`

- **做什么**：把 `LightRejectReason` / `LightDetectionStats` / `LightRejection` / `LightDetectionResult` 从 `light_detector.hpp` 搬到 `core/light_result.hpp`；`light_detector.hpp` 改成 include 它；`armor_refiner.hpp` 的 include 从 `light_detector.hpp` 改为 `light_result.hpp` + `light_bar.hpp`。
- **落点**：新文件 + `light_detector.hpp:14`、`armor_refiner.hpp:14`。
- **验收**：`grep -rn "light_detector.hpp" framework/algorithm/vision` 的结果里**不再出现 `armor_refiner.hpp`** ✗→✓；编译 0 错误。
- **失败分叉**：若精修器编译报缺 `LightBar` → 说明它其实还需要 `core/light_bar.hpp`，补上即可（这正是"头文件自带依赖"的检查点）。

### 步骤 3：`core/light_bar.hpp/.cpp`

- **做什么**：`LightBarGeometry` + `LightBar`（含 `FromEndpoints` 内联实现）搬到 `core/light_bar.hpp`，`LightBar::Create` / `CreateFromEndpoints` 的**实现**搬到 `core/light_bar.cpp`（从 `armor.cpp` 剪出来，原样不改）。
- **落点**：新头 + 新源；`armor.cpp` 删掉这两段；`light_detector.hpp` 改为 include `core/light_bar.hpp`。
- **验收**：`armor.cpp` 行数从 509 降到 ~300；`wc -l core/light_bar.cpp` 约等于搬走的行数。
- **失败分叉**：若链接报"undefined `LightBar::Create`" → 新 `.cpp` 没进 CMake（见步骤 6）。

### 步骤 4：`core/armor_board.hpp/.cpp`（几何配对）

- **做什么**：`ArmorMetrics` / `ArmorCandidate` / `PairRejectReason` / `PairResult` / `ArmorGeometry` 搬过去，cpp 侧对应实现（构造、`Pair`、`CornersInsideImage`、`ResolveLightConflicts`、两个 `Validate`）一起搬。
- **落点**：新头 + 新源；`armor.cpp` 剩下来的就是 `DetectedArmor::Create` 与解码函数（步骤 5 处理）。
- **验收**：`core/armor_board.hpp` ≤ 400 行；`armor.cpp` 只剩检测契约那部分（~150 行）。
- **失败分叉**：若 `ArmorCandidate` 找不到 `LightBar` → 补 `core/light_bar.hpp`（步骤 2/3 已经建好）。

### 步骤 5：`detect/model_decode.hpp/.cpp`，`armor.hpp` 退场

- **做什么**：`DetectedArmor*` 三个类型（含 `DetectedArmor::Create` 实现）搬 `core/detections.hpp`；`DecodeArmorModelColor/Label/Size`、`IsArmorLabelCompatibleWithSize` 搬 `detect/model_decode.hpp/.cpp`；**删除 `armor.hpp` / `armor.cpp`**（内容已全部落到新文件）。
- **落点**：新 4 个文件；`armor_detector.hpp/.cpp`、`light_detector.cpp` 的 include 改成新路径。
- **验收**：`ls framework/algorithm/vision` 里没有 `armor.hpp|armor.cpp`；`grep -rn "vision/armor.hpp" framework project` 为空；编译 0 错误。
- **失败分叉**：若某个 `.cpp` 报缺类型 → 看它 include 的头是否少了 `core/*.hpp`（按"自己 include 自己需要的"补齐）。

### 步骤 6：构建与外部引用收口

- **做什么**：`framework/CMakeLists.txt` 的 `framework_vision` 源列表换成新路径（4 个源 → 6 个源）；`project/thread/vision/trd_vision.cpp` 的 include 改成 `framework/algorithm/vision/detect/armor_detector.hpp`。
- **验收**：`grep -n "algorithm/vision" framework/CMakeLists.txt` 里没有 `${PROJECT_SOURCE_DIR}` 拼错；`trd_vision.cpp` 只 include 一个 vision 头（检测器），它不需要也不许 include `core/` 细节。
- **失败分叉**：若 `framework_vision` 报源文件不存在 → 步骤 1~5 某步的文件名与 CMake 不一致，按实际文件名改 CMake（不要反过来改文件）。

## 6. 顺序为什么不能换

- **先 `core/` 后 `detect/refine/`**：core 是最底层，拆它才是"切断下游依赖"的前提；反过来先搬检测器，会因为找不到 `LightBar`/`TeamColor` 而中断。
- **步骤 2 必须在步骤 5 之前**：`refine → detect` 那条横跨边要在 `core/light_result.hpp` 建好之后才有地方落，否则精修器无处可依。
- **步骤 5 删除 `armor.hpp` 必须最后**：它现在是所有文件的公共依赖点，提前删会让 5 个文件同时报错，定位成本高。
- **步骤 6 最后**：CMake 与外部引用只在文件路径稳定之后改一次，避免中途反复改。

## 7. 失败回退表

| 症状 | 先查 | 最后才查 |
| --- | --- | --- |
| "重复定义" | 旧文件里的那份有没有删干净 | 是否两处都 include 了不同路径的同名头 |
| "不完整类型" | 新头有没有 include 它用到的类型所在头 | 是否存在循环 include（core 之间互相依赖） |
| 链接期 undefined | 新 `.cpp` 是否进了 `framework_vision` | 函数声明与定义是否落在不同层 |
| 编译通过、运行行为变了 | 搬运时是否改了实现（逐段核对搬走的代码） | 是否多删了内联函数体 |
| 外部（`trd_vision`）报错 | 它的 include 路径改没改 | 它是否误 include 了 `core/` 内部头 |

## 8. 明确不做

1. **不改 namespace**（保持 `algorithm::vision`），不改类名与函数签名；
2. **不动任何算法与实现**——只搬文件、改 include；搬完用"去掉注释后逐字节比对"证明与原文一致；
3. **不改 `framework/algorithm/` 的其他子目录**（`math/`、`controller/`、`filter/`、`observer/`）；
4. **不引入构建期检查脚本**（分层规则先靠人看，等文件多了再谈）。
