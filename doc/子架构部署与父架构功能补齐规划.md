## 2. 平台映射（移植的唯一依据）

### 2.1 线程故障

| 父架构（Zephyr） | 子架构（Linux） | 理由 |
|---|---|---|
| `TaskResult{Continue, Retry, Exit}` | 同，`Fatal` **改名** `Exit` | 语义一致：跳过 RetryHook，直接交 `DefaultHandle` |
| `RetryHook = bool(void*)` | `RetryHook = RecoveryAction(*)(const std::exception&, Thread&, void*)` | Linux 有异常；相机要靠异常类型判可恢复、靠 `Thread&` 调 `WaitForStop` |
| `ExitHook = void(void*)` | 同 | — |
| `ThreadFaultPolicy{Isolate, Recover}` | 同 | — |
| `keep_alive` | 同，但含义收窄为「`Recover` 处置时**不主动请求**该线程停止」 | Linux 不能强杀，只能请求；见 §2.2 |
| `Exit()` = `k_thread_suspend` + `ExitHook` + 注销 + `k_thread_abort` | `Exit()` = `RequestStop()`；亡语与注销由**目标线程自己在 `Run()` 收尾路径**执行 | pthread 不能安全强杀；协作式反而让亡语一定跑在目标线程自己的栈上 |
| `Halt()` = 长鸣 + 逐个处决 + `while(1)` | `DefaultHandle(Recover)` = 逐个 `Exit()` 非 `keep_alive` 线程，**不请求进程停止** | 对应父架构「全杀但留 shell 作观察窗口」；进程由 Ctrl+C 收尾 |
| 亡语在被处决线程的**调用者**栈上执行（父架构的能力边界） | 亡语在目标线程**自己的**栈上执行 | Linux 协作式退出的额外收益 |

### 2.2 `keep_alive` 在 Linux 上为什么还有意义

父架构里它的作用是「`Halt()` 遍历注册表时跳过这一项」。子架构照搬这个**判定位置**即可：

```text
Recover 处置：
  for 注册表每一项 t:
      t == 故障线程        → 跳过（它马上要从 Run 返回）
      t->KeepAlive()       → 跳过（shell 留下）
      其他                 → t->Exit()（= RequestStop，异步）
  不调 System_RequestStop
```

结果：业务线程全部退出，`shell` 仍在跑，`thread list` 还能敲、日志还能发、终端还能用。进程要退出就 Ctrl+C，`System_Shutdown` 会正常 stop/join 全部（含 shell，它的 join 会 `Log::Flush`）。

**这与父架构行为一致，不是假保护。** 唯一的差别是父架构的 `Halt()` 里 `while(1)` 永不返回，子架构是进程继续跑但业务已停。

### 2.3 日志

| 父架构 | 子架构 | 处理 |
|---|---|---|
| 四层目录 `cmd/ process/ queue/ transport/` | 平铺在 `log/` 下 | **搬**目录结构 |
| `irq_lock` 临界区 | `std::mutex` | 不搬 |
| 参数快照 + shell 线程展开 | 调用点 `vsnprintf` 成 `text[512]` | **不搬**，见 §7 |

### 5.3 步 1-1：`token.hpp` 追加内容

在 `namespace debug { ... }` 末尾（`NextToken` 之后）追加，逐字照父架构 `framework/shell/token.hpp:55-95`：

```cpp
/**
 * @brief 子命令表项：子命令名 + 处理函数
 *
 * 处理函数收到的 args 是「子命令之后剩余的行」（已跳过空格、可再取 token）。
 */
struct SubCmdEntry
{
    const char* name;                    // 子命令名（如 "list" / "on"）
    void      (*handler)(uint8_t* args); // 处理函数
};

/**
 * @brief 词法解析 + 查表匹配：取出首 token 作子命令名，命中则调处理函数
 *
 * 未命中时调用 on_unknown（传子命令之后的剩余行）。
 *
 * @param line       命令行（原地修改，token 间空格变 '\0'）
 * @param table      子命令表
 * @param count      表项数
 * @param on_unknown 未命中时的处理函数（通常打印 usage）
 * @return true=命中；false=未命中（on_unknown 已调用）
 */
inline bool DispatchSubCmd(uint8_t* line, const SubCmdEntry* table, size_t count, void (*on_unknown)(uint8_t* args))
{
    const char* sub = nullptr;

            return true;
        }
    }

    }
    return false;
}
```

## 6. P2：线程故障处置

> **P2 拆成 11 步。**

### 6.1 目标语义

| 策略 | 影响面 | 处置 | 系统后续 |
|---|---|---|---|
| `Isolate` | 小（vision / calib / test） | 该线程执行亡语 → 注销注册表 → 自己退出 | 其他线程照常 |
| `Recover` | 大（camera / shell） | 逐个 `Exit()` 所有非 `keep_alive` 线程 | 业务全停，`shell` 存活供观察；进程不退出 |

**判定入口只有一个**：`Task` 抛异常或返回 `Retry`，且 `RetryHook` 返回 `Stop`（或没装钩子）；或 `Task` 返回 `Exit` 且**不是**停机路径。

### 6.3 步 2-1：`thread_fault.hpp` 全文

```cpp
/**
 * @file thread_fault.hpp
 * @author qingyu
 * @brief 线程故障策略、钩子类型、配置结构与默认处置函数
 * @version 0.1
 * @date 2026-10-27
 *
 * @copyright Copyright (c) 2026
 *
 */

#pragma once

#include <cstdint>

class ThreadBase;
class Thread;

/**
 * @brief 线程故障策略：声明本线程出故障时的影响面
 */
enum class ThreadFaultPolicy : uint8_t
{
    Isolate = 0,    // 影响小：收尾后退出，不拖累系统
    Recover = 1,    // 影响大：救不回来时停掉全部业务线程，保留 shell
};

/**
 * @brief 异常恢复结果：正常停止由线程停止标志单独判断
 */
enum class RecoveryAction
{
    Restart,    // 恢复成功，重新执行任务入口
    Stop        // 无法恢复，交给 DefaultHandle 按策略处置
};

/**
 * @brief Retry 钩子：Task 抛异常或返回 Retry 时由线程自己就地处理
 *
 * Linux 版带异常与线程引用（父架构无异常，故为 bool(void*)）：
 * 相机要靠异常类型判可恢复性，靠 Thread& 轮询 WaitForStop 重连。
 */
using RetryHook = RecoveryAction (*)(const std::exception&, Thread&, void*);

/**
 * @brief 退出钩子（亡语）：线程临死前最后一次发言
 *
 * 只负责收尾与交代后事，不负责杀线程。由 Run() 的收尾路径唯一触发。
 */
using ExitHook = void (*)(void* context);

/**
 * @brief 线程故障配置
 *
 * 由 Thread::Start() 的第 5 个参数传入，与线程名同处一个调用点。
 */
struct ThreadFaultConfig
{
    RetryHook         retry      = nullptr;                        // 异常恢复钩子
    ExitHook          exit       = nullptr;                        // 亡语
    ThreadFaultPolicy policy     = ThreadFaultPolicy::Recover;     // 故障策略
    bool              keep_alive = false;                          // Recover 处置时是否跳过本线程
};

/**
 * @brief 默认故障处置函数：按线程声明的策略兜底
 *
 * 弱符号，项目可在自己编译单元里重定义同名函数整体替换。
 *
 * @param thread 出故障的线程
 */
__attribute__((weak)) void DefaultHandle(ThreadBase* thread);
```

**注意 include**：`std::exception` 需要 `<exception>`。上面漏了会编不过，**必须写 `#include <exception>`**。

### 6.4 步 2-2：`thread_fault.cpp` 全文

```cpp
/**
 * @file thread_fault.cpp
 * @author qingyu
 * @brief 线程故障默认处置函数的弱实现
 * @version 0.1
 * @date 2026-10-27
 *
 * @copyright Copyright (c) 2026
 *
 */

#include "thread_fault.hpp"
#include "thread.hpp"
#include "thread_registry.hpp"
#include "log.hpp"

/**
 * @brief 默认处置：按线程声明的策略兜底
 *
 * 只在 RetryHook 处理不了故障时进入，即「任务自己已经救不回来了」。
 *
 * @param thread 出故障的线程
 */
void DefaultHandle(ThreadBase* thread)
{
    if (thread == nullptr)
    {
        DUST_LOG_ERR("thread fault with null thread");
        System_RequestStop(1);
        return;
    }

    switch (thread->FaultPolicy())
    {
        case ThreadFaultPolicy::Isolate:
        {
            // 影响小：收尾后自己退出，不拖累系统
            DUST_LOG_WRN("thread %s fault, isolating", thread->Name());
            thread->Exit();
            return;
        }

        case ThreadFaultPolicy::Recover:
        default:
        {
            // 影响大且无法恢复：停掉全部业务线程，shell 留下供观察
            DUST_LOG_ERR("thread %s fatal, stopping all threads", thread->Name());

            for (uint8_t i = 0; i < thread_registry::Count(); ++i)
            {
                ThreadBase* t = thread_registry::At(i);
                if (t == nullptr || t == thread || t->KeepAlive()) continue;
                t->Exit();      // 协作式：只请求停止，不 join，注册表项由目标线程自己移除
            }
            return;             // 故障线程自己从 Run 返回，进程继续（shell 存活）
        }
    }
}
```

**必须补的 include**：`System_RequestStop` 在 `framework/init/startup/System_startup.hpp`；`log.hpp` 的路径取决于当前目录（子架构用 `#include "framework/cmd/shell/log/log.hpp"` 或 CMake 已加的 include 目录 `log/`，两种都行，**按同目录其他文件写法**：`trd_camera.cpp` 用完整路径，`shell.cpp` 用短路径）。

**关键差异说明**：`Exit()` 不 join、不立即注销，所以循环里 `Count()` 不会在遍历中缩小，用 `++i` 而不是父架构那种"删除后原地补位"的写法。

#### ⑦ 新增 `Exit()` 实现

```cpp
/**
 * @brief 请求终止线程：置停止标志并唤醒所有等待点
 *
 * 协作式：目标线程从 Run 返回时执行亡语并注销注册表，本函数不 join。
 * 带保留标记的线程（shell）拒绝退出。
 */
void Exit() override
{
    if (fault_.keep_alive)
    {
        DUST_LOG_WRN("thread %s is reserved, exit refused", Name());
        return;
    }
    RequestStop();
}

ThreadFaultPolicy FaultPolicy() const override { return fault_.policy;   }
bool              KeepAlive()   const override { return fault_.keep_alive; }
```

**为什么 `Exit()` 不 join**：`Exit()` 可能由故障线程自己调用（`DefaultHandle(Isolate)` 里），自己 join 自己会死锁。他杀时 join 也会阻塞调用者（可能是 shell 命令线程），而目标线程可能正阻塞在 `poll` 上——虽然 `RequestStop` 会唤醒它，但 shell 命令线程不该等。join 统一交给 `System_Shutdown`。

## 7. P3：启动期耗时 `boot timing`

> **P3 拆成 10 步。**
> 用户说"开始 P3 第 N 步"= 只改表格里那一个文件，改完停下报告，等"继续"。

### 7.1 设计

照父架构：每个 `REGISTER_INIT` / `REGISTER_THREAD` 展开时**额外生成一个耗时槽**放进 `.boot_timing` 段，启动器在每项执行前后取时间写进槽，`boot timing` 命令遍历段按耗时降序输出。槽数量由链接器决定，没有固定数组。

### 7.3 步 3-1 / 3-2：`boot_timing` 全文

`boot_timing.hpp`：

```cpp
/**
 * @file boot_timing.hpp
 * @author qingyu
 * @brief 启动期耗时槽 — 每个注册项一个槽，链接段收集，无固定数组
 * @version 0.1
 * @date 2026-10-27
 *
 * @copyright Copyright (c) 2026
 *
 */

#pragma once

#include <cstdint>

/**
 * @brief 启动期耗时槽
 *
 * 由 REGISTER_INIT / REGISTER_THREAD 各生成一个，放进 .boot_timing 段。
 * 槽数量由链接器按实际注册项决定，无需固定容量。
 */
struct BootTimingSlot
{
    const char* name;   // 项目名（字符串字面量）
    uint64_t    ns;     // 耗时（纳秒），启动期由启动器写入
    bool        ok;     // 是否成功，启动期由启动器写入
};

/**
 * @brief 启动期耗时记录（操作链接段内的槽）
 */
class BootTiming
{
public:
    /**
     * @brief 记录一个槽的耗时
     * @param slot 槽指针（注册宏生成）
     * @param ns   耗时（纳秒）
     * @param ok   是否成功
     */
    static void Record(BootTimingSlot* slot, uint64_t ns, bool ok)
    {
        if (slot == nullptr) return;
        slot->ns = ns;
        slot->ok = ok;
    }

    static uint8_t Count();
    static const BootTimingSlot* At(uint8_t index);
    static uint64_t TotalNs();
};
```

`boot_timing.cpp`：逐字照父架构，只把段边界符号名保持一致：

```cpp
#include "boot_timing.hpp"

extern const BootTimingSlot __boot_timing_start[];
extern const BootTimingSlot __boot_timing_end[];

uint8_t BootTiming::Count()
{
    return static_cast<uint8_t>(__boot_timing_end - __boot_timing_start);
}

const BootTimingSlot* BootTiming::At(uint8_t index)
{
    if (index >= Count()) return nullptr;
    return &__boot_timing_start[index];
}

uint64_t BootTiming::TotalNs()
{
    uint64_t sum = 0;
    const uint8_t count = Count();
    for (uint8_t i = 0; i < count; ++i) sum += __boot_timing_start[i].ns;
    return sum;
}
```

**槽结构里 `ns` 用 `uint64_t` 而不是父架构的 `uint32_t`**：父架构 uint32 上限 4.29 s，MCU 启动项都在毫秒级够用；Linux 上 `camera_init` 会**阻塞等设备插上**（`trd_camera.cpp:60-94` 的 `for(;;)` 循环），可能等几分钟，`uint32_t` 会溢出成荒谬值。**这是刻意的平台差异，不是抄漏。**

## 8. P4：DUST_LOG 四层重构

### 8.1 目标与红线

### 9.4 步 5-3：分频与列表

```cpp
/**
 * @brief 分频过滤：本条 DBG 是否放行
 *
 * divisor<=1 时直接放行（短路，不碰 quota）；
 * 否则递减配额，配额用尽则放行并重填。
 */
bool PassDivisor(LogEntry* e)
{
    const uint16_t divisor = e->divisor.load();
    if (divisor <= 1) return true;

    if (e->quota.fetch_sub(1) > 0) return false;   // 还有配额：丢弃
    e->quota.store(static_cast<uint16_t>(divisor - 1));   // 配额用尽：放行并重填
    return true;
}
```

`Debug()` 开头（在锁内、`va_start` 之前）加：

```cpp
    if (!PassDivisor(e)) return;
```

```cpp
    if (*rest != '\0')
    {
        uint32_t v = 0;
        for (const uint8_t* p = rest; *p >= '0' && *p <= '9'; ++p)
        {
            v = v * 10u + static_cast<uint32_t>(*p - '0');
            if (v > 0xFFFFu) { v = 0xFFFFu; break; }
        }
        divisor = (v == 0) ? 1 : static_cast<uint16_t>(v);
    }
```

## 11. 不搬清单（含理由）

| # | 父架构的东西 | 为什么不搬 |
|---|---|---|
| 1 | **参数快照记录队列**（`LogRecordQueue` / `BuildRecordFromVaList` / `FormatRecordToText` / `kMaxLogArgs`） | 子架构在调用点 `vsnprintf` 成 `text[512]`。父架构做快照是因为 MCU 上要在 shell 线程里格式化以省调用点开销（1kHz 循环），且参数槽只有 32 位、`%f` 要拆两槽。Linux 有完整 libc 与互斥锁，再引入 32 位槽等于**主动降级**。**代价**：每次日志持锁格式化；当前视觉链的日志频率（每秒 1 条汇总 + DBG）远低于瓶颈，不需要优化。 |
| 2 | `irq_lock` 临界区 | 子架构用 `std::mutex`，已在 `log.cpp` 里。 |
| 3 | DMA 发送泵（`Stream*` / `k_sem_give` / `HandleTxDone`） | 子架构写 `stderr`，同步。`eventfd` + `poll` 已经承担"唤醒 shell 线程"的作用。 |
| 4 | `ThreadPrio` | `std::thread` 无优先级。父架构的 7 档在 Linux 上要么映射到 `nice`（影响整个进程）要么用 `sched_setscheduler`（要权限），都不是"线程模板"该管的事。 |
| 5 | 线程调度开销统计（`max_overhead_ns` / `last_overhead_ns`） | 这是父架构 2026-10-26 "算一下 Run 循环要多久"那次需求的产物，目的是量化**外壳自身**开销。子架构的 `Thread::Run` 每拍只有几次原子操作与一次条件变量判断，没有量化需求。**若以后要，单独提。** |
| 6 | `stack_unused`（`k_thread_stack_space_get`） | Linux 无法在运行期可靠查询 `std::thread` 的栈余量（`pthread_getattr_np` 只给栈边界，不给水位）。 |
| 7 | `REGISTER_THREAD` 的 `fail` 策略（`HaltOnFail` / `ContinueOnFail`） | 子架构线程启动失败一律 `System_RequestStop(1)` 并中止后续。改成带策略要动 `REGISTER_THREAD` 的 5 参数签名 + 5 处调用点 + `Init_entry.cpp` 分支，属于**另一个需求**（"哪些线程允许起不来"），不在本次范围。 |
| 8 | `Halt()` 里的 `EXEC_BUZZER_LONG()` | 子架构无蜂鸣器。 |
| 9 | `.thread_fault` 链接段 + `REGISTER_THREAD_FAULT` + `FindThreadFault` | 父架构已经**废弃**这套（`线程故障配置注册表vs调用点规划.md` 拍板走 B：配置进 `Start()` 参数）。子架构直接上 B，不经过 A。 |
| 10 | `boot_timing.ld` 用 `SECTION_DATA_PROLOGUE` / `GROUP_DATA_LINK_IN` | 那是 Zephyr 链接器语法。子架构是裸 GNU ld，直接写 `SECTIONS { ... } INSERT AFTER .data`。 |
| 11 | `kShellCmd_##ident` 的 `_CONCAT`（来自 `<zephyr/toolchain.h>`） | 子架构用自写的两层 `DUST_CAT`（§5.4）。 |
| 12 | 父架构 `LogEntry` 的 `const char* name` | 子架构用 `std::string`（调用点可能传临时串）。**只搬字段，不搬类型。** |
