# 复用 0526 四点 YOLO 的装甲板识别快速接入规划

日期：2026-10-14。

状态：**规划已重写，尚未实施模型接入。** 本文只规划如何复用
`temp/Dust_infantry_vision-main/assets/0526.onnx`，不授权创建新的源码目录或文件，
不授权安装依赖、生成 TensorRT engine 或修改运行时代码。

## 1. 结论先行

当前最快可落地的路线不是继续调传统灯条，也不是重新训练模型，而是完整复现参考工程已经使用的
`0526` 四关键点 YOLO 推理契约：

```text
当前海康相机 BGR 帧
→ 640×640 左上放置预处理
→ 0526 TensorRT engine
→ [1, 25200, 22] 原始输出
→ 四点/颜色/标签解析
→ 置信度过滤与 NMS
→ trd_vision 输出识别结果
```

第一版只做**全图、单请求、同步、模型直出**，目的就是尽快回答“现有模型在当前相机画面上能不能识别装甲板”：

- 使用且只使用 `0526.onnx`，不使用 `tiny_resnet.onnx`；
- 不训练、不整理训练数据、不创建训练脚本；
- 不使用备用的 `yolov5.xml/.bin` 冒充当前模型；
- 不在第一版启用传统灯条精修、`ArmorRefiner`、动态 ROI、异步请求池；
- 不先做 PnP、跟踪、预测、云台或开火；
- 不把“模型成功加载”当成“识别成功”，必须用真实相机画面看到四点、颜色、标签和置信度。

推理后端固定为 **TensorRT 10.x**。原因不是偏好，而是当前证据已经排除了“直接用现有 OpenCV DNN”这条捷径：

1. 当前机器有 RTX 4060 Laptop GPU，NVIDIA 驱动 595.84 正常，具备走 TensorRT 的硬件条件；
2. 当前没有 CUDA Toolkit、TensorRT、OpenVINO 或 ONNX Runtime；
3. 系统 OpenCV 4.6.0 读取 `0526.onnx` 时直接报错：`Unsupported data type: FLOAT16`；
4. 参考工程当前配置本来就是把 `0526.onnx` 转成本机 `.engine` 后用 TensorRT 运行；
5. TensorRT engine 与 GPU、CUDA、TensorRT 版本绑定，仓库里没有可直接复用的 `.engine`，必须在这台机器生成。

因此真正的最短路径只有四步：先补齐 TensorRT 运行条件，再生成本机 engine，再按参考源码原样实现预处理/后处理，最后接入现有识别线程。任何跳过第一步而直接写 C++ 推理代码的方案都无法在当前机器上运行。

## 3. 必须逐字复现的模型契约

### 3.1 预处理

输入只接受非空 `CV_8UC3` BGR 图像。对整帧按参考代码执行：

```text
scale = min(640 / source_width, 640 / source_height)
resized_width  = int(source_width  × scale)
resized_height = int(source_height × scale)
```

随后：

1. 创建全零的 `640×640×3` 输入图；
2. 把缩放图放在 `(0, 0)`，即左上角；
3. 只在右侧或下侧补黑边，不做居中 letterbox；
4. BGR 转 RGB；
5. 每个通道除以 `255.0`；
6. HWC 转成连续 NCHW，输入 shape 固定为 `[1,3,640,640]`。

禁止改成居中填充、保持 BGR、减均值、除标准差或直接拉伸到正方形。任一变化都会改变模型输入分布和坐标还原方式。

### 3.2 22列输出

每一行定义如下：

| 列 | 含义 | 处理 |
| --- | --- | --- |
| `0..7` | 四个原始关键点 `p0,p1,p2,p3` | 每个坐标除以 `scale` 回到原图 |
| `8` | objectness logit | 先做 sigmoid |
| `9..12` | 4色 logits | 只做 argmax |
| `13..21` | 9标签 logits | 只做 argmax |

参考解析器不是按原始点序直接输出，而是固定重排为：

```text
corners = [p0, p3, p2, p1] = [左上, 右上, 右下, 左下]
```

轴对齐框只能由重排后的四点取 `min/max` 计算，不能把框的四角当成模型关键点。

### 3.3 颜色、标签和尺寸映射

`0526` 的颜色顺序固定为：

```text
0 blue, 1 red, 2 gray/extinguish, 3 purple
```

快速打通阶段同时保留 `blue` 和 `red`，用于现场核对颜色映射；gray 与 purple 必须明确计入拒绝统计，不能映射成红或蓝。敌方颜色过滤等配置文件获得单独授权后再增加。

9个标签索引必须按参考构造函数解释：

| 索引 | 标签 | 尺寸 | 第一版处理 |
| ---: | --- | --- | --- |
| 0 | sentry | small | 接受 |
| 1 | one | big | 接受 |
| 2 | two | small | 接受 |
| 3 | three | small | 接受 |
| 4 | four | small | 接受 |
| 5 | five | small | 接受 |
| 6 | outpost | small | 接受 |
| 7 | base | small | 按参考 `check_type()` 拒绝 |
| 8 | base | big | 接受 |

不得用当前 `ArmorLabel` 枚举的整数顺序直接强转；必须显式 `switch` 映射，否则 sentry、one 和 base 会整体错位。

### 3.4 阈值与 NMS

第一版完全使用参考值，不先调参：

- 候选预筛：`sigmoid(objectness) >= 0.7`；
- NMS：对四点外接轴对齐框执行 `cv::dnn::NMSBoxes`，score threshold `0.7`，NMS IoU `0.3`；
- NMS 后再要求 `confidence > 0.8`，所以最终有效门槛是严格大于 `0.8`；
- NMS 后拒绝不合法尺寸/标签组合以及 gray/purple；红、蓝在第一轮都保留；当前9路显式映射本身不会产生 `not_armor`；
- 保留原始四点，NMS 只决定候选是否留下，不改四点坐标。

第一轮实机结果出来之前，不得降低 `0.8` 来制造“识别到了”的假象。

## 4. 最短实施路径

### P0：推理环境门禁，不改业务代码

此步骤需要用户另行明确授权安装依赖；本文不构成安装授权。

目标是让当前机器同时具备：

```text
CUDA Toolkit 12.x（含 nvcc、cudart，与参考工程约束一致）
TensorRT 10.x（含 NvInfer.h、libnvinfer.so、trtexec）
```

开始写推理代码前必须全部通过：

```text
nvidia-smi                     # RTX 4060 和驱动正常
nvcc --version                 # CUDA Toolkit 实际版本可见
trtexec --help                 # 工具存在；版本再由包信息/NvInferVersion.h核对
NvInfer.h / libnvinfer.so      # C++ 编译和链接资产存在
```

不能把 `nvidia-smi` 显示的“CUDA Version 13.2”当成 CUDA Toolkit 已安装；它只说明驱动可支持的最高 CUDA 运行级别。当前现场正是“驱动正常，但 nvcc/TensorRT 不存在”。

环境通过后，在现有生成目录中创建本机 engine：

```text
输入：temp/Dust_infantry_vision-main/assets/0526.onnx
输出：build/0526.engine
```

第一版按参考工程的 FP32 compute 路线生成，不主动加 `--fp16`、INT8 或动态 shape。命令骨架为：

```bash
trtexec \
  --onnx=temp/Dust_infantry_vision-main/assets/0526.onnx \
  --saveEngine=build/0526.engine \
  --skipInference
```

实际执行前先以安装后的 `trtexec --help` 核对该版本参数；若命令或模型解析失败，P0 失败并停止，不能改用备用模型掩盖。

engine 只属于当前机器的 `build/` 产物：不复制到源码目录、不提交、不改名伪装成通用模型。换 GPU、TensorRT 或 CUDA 后必须重建。

### P1：现有文件内完成模型直出闭环

P1 不新增目录或源码文件，只修改下面这些现有文件。

#### `CMakeLists.txt`

- OpenCV 组件增加 `dnn`，只用于 `blobFromImage` 和 `NMSBoxes`；
- `find_package(CUDAToolkit 12 REQUIRED)`；

不增加第二套构建入口，不引入 OpenVINO/ONNX Runtime，不下载模型。

#### `framework/CMakeLists.txt`

- `framework_vision` 增加 `opencv_dnn`、`CUDA::cudart` 和 `nvinfer`；
- TensorRT 头文件只作为 `framework_vision` 的私有依赖；
- 保持 `armor.cpp`、`armor_detector.cpp` 等现有源文件列表，不新增平行算法模块。

#### `project/CMakeLists.txt`

- `vision_app` 明确链接现有 `framework_vision`；
- 不把算法 `.cpp` 再直接塞入 `vision_app`，避免重复定义。

#### `framework/algorithm/vision/armor.hpp`

现有 `ArmorCandidate` 由两根灯条构造，不能拿网络四点硬造两根假灯条。应在同一文件内增加独立的模型结果类型，例如 `DetectedArmor`，至少保存：

```cpp
std::array<cv::Point2f, 4> corners;  // LT, RT, RB, LB
cv::Point2f center;
cv::Rect2f bounding_box;
TeamColor color;
ArmorLabel label;
ArmorSize size;
float confidence;
int raw_color_id;
int raw_label_id;
```

`ArmorLabel` 必须通过显式映射填写，不能直接把9路索引强转成枚举。传统 `LightBar`、`ArmorCandidate` 和 `ArmorGeometry` 保留，但不参与第一版模型路径。

#### `framework/algorithm/vision/armor_detector.hpp`

把现有 `ArmorDetector` 变成 0526 模型检测入口，仍沿用当前文件和类名，不新建 `yolo_detector.*`：

- `Config` 只保留 engine 路径、CUDA device、`0.7/0.8/0.3` 阈值；
- 用私有 `Impl` 隔离 TensorRT 头文件和资源；
- 构造时一次加载 engine 并校验张量，不允许每帧加载；
- `Detect()` 接收只读 `CV_8UC3` BGR 图像，返回 `DetectedArmor` 列表与逐级统计；
- `Detect()` 不再声明为 `const`，因为 execution context、stream 和缓冲区会被复用。

第一版统计至少包含：

```text
raw_rows / score_passed / nms_kept / accepted
rejected_color / rejected_label_type / rejected_geometry
preprocess_ms / inference_ms / postprocess_ms
```

#### `framework/algorithm/vision/armor_detector.cpp`

只实现一个同步 TensorRT context：

1. 读取 `build/0526.engine`；
2. 校验恰好一个输入、一个输出；
3. 输入必须是静态 `[1,3,640,640]`，类型只接受 FP32 或 FP16；
4. 输出必须是 FP32 `[1,25200,22]` 或 `[25200,22]`；
5. 创建一个 CUDA stream 和一组可复用 host/device buffer；
6. 每帧严格执行第3章预处理；
7. `enqueueV3()` 后同步等待；
8. 严格执行第3章后处理；
9. 任一 CUDA/TensorRT 错误抛出明确异常，由现有线程错误流程停机，不无限重试。

第一版只有一个 context 是刻意的：当前相机通道已经是“最新帧覆盖”，同步推理慢时自然丢旧帧，不需要先复制参考工程的请求池和有序交付。

#### `project/thread/vision/trd_vision.cpp`

- `thread_init()` 构造唯一 `ArmorDetector`，engine 加载失败直接让初始化失败；
- 检测器由 vision 模块自己的 `std::unique_ptr` 持有，并给现有 init 注册清理回调；线程 join 后再释放 TensorRT/CUDA 资源；
- `Task()` 每次取到最新相机帧后调用 `Detect()`；
- 第一轮同时保留红、蓝检测结果，用日志核对模型颜色映射，不先加敌方颜色过滤；
- 每秒只输出一条汇总：识别 FPS、订阅丢帧、候选数、接受数、三段耗时；
- 有识别时同时输出最高置信目标的颜色、标签、置信度和四点，但最多每秒一次；
- 停止顺序继续依赖相机通道关闭唤醒，不新增队列和线程。

P1 的“识别出来”定义为：真实相机对准一块已知装甲板时，日志持续给出合理的颜色、标签、置信度和四点坐标。它只证明模型链打通，还不证明最终精度达标。

### P2：同帧可视化，需要单独授权结果话题

正确的可视化必须让 display 获得“模型处理的那一帧 + 该帧四点”，不能让 display 从另一个时刻的相机帧上硬套结果，也不能让 vision 原地修改 `camera_to` 共享像素。

按当前架构，干净的做法需要一个 `vision_to` 单槽结果话题。由于用户已经明确禁止未经允许创建目录或文件，实施到这里必须暂停并单独申请以下唯一新增项：

```text
framework/topic/vision_to/vision_to.hpp
```

只有用户明确批准后才允许创建。该消息只包含：

```cpp
cv::Mat source_image;  // 与推理输入同一帧的浅引用
std::chrono::steady_clock::time_point timestamp;
std::vector<DetectedArmor> armors;
double processing_ms;
```

随后修改现有文件：

- `trd_vision.cpp`：每处理完一帧发布一次，零目标也发布；
- `trd_display.cpp`：改订阅 `vision_to`，对 `source_image.clone()` 画四边形、颜色、标签、置信度；
- display 仍是唯一窗口拥有者，vision 算法不 `imshow()`、不保存图片。

如果用户不批准这个文件，P2 不实施；不得用全局裸指针、跨线程静态容器或把结果塞进 `camera_to.hpp` 来绕过授权。

### P3：模型直出稳定后才考虑精修

P3 不是快速识别的前置条件。只有模型已经能稳定给出粗四点，但角点误差确实影响后续 PnP 时，才允许把现有 `ArmorRefiner` 作为可关闭后处理接回：

- 输入必须是 YOLO 左右边缘先验；
- 左边只选距 YOLO 左边缘最近的灯条，右边同理；
- 两侧距离门禁都通过才替换四点，否则完整保留 YOLO 原四点；
- 禁止重新枚举 ROI 内任意灯条对，也禁止让精修失败删除一个原本有效的 YOLO 目标。

当前 T1 报告已经证明旧精修结果未达标，所以它默认关闭，不能阻塞 P1/P2。

P0 全部满足才允许进入 P1：

1. `0526.onnx` 哈希仍为本文第2.1节记录值；
2. `trtexec` 成功生成非空 `build/0526.engine`；
3. engine 只含一个输入和一个输出；
4. 输入静态 shape 为 `[1,3,640,640]`；
5. 输出为 FP32 `[1,25200,22]` 或等价的 `[25200,22]`；
6. engine 能在 GPU 0 上完成至少一次推理，无 CUDA/TensorRT 错误；
7. 记录实际 CUDA Toolkit、TensorRT、驱动和 GPU 型号，不能只写“已安装”。

### 6.2 P1 编译与初始化

至少执行：

```bash
cmake -S . -B build \
  -DTensorRT_ROOT=<实际 TensorRT 根目录> \
  -DARMOR_ENGINE_PATH="$PWD/build/0526.engine"
cmake --build build --target vision_app -j2
```

通过条件：

- CMake 明确打印找到的 TensorRT 版本、头文件、库和 engine 路径；
- `vision_app` 动态依赖中能看到正确的 `libnvinfer` 与 `libcudart`；
- 程序初始化日志打印 input/output 名称、类型、shape 和 CUDA device；
- engine 缺失、版本不兼容或 shape 不符时，初始化失败并给出具体原因，不能运行到首帧才崩溃。

### 6.3 P1 真实相机识别

运行现有程序并打开 vision DBG：

```text
dust run
log on vision
```

把一块已知红/蓝、已知编号的装甲板放入当前相机画面，逐步检查：

1. `raw_rows` 固定为 `25200`；
2. `max_objectness`、`score_passed`、`nms_kept` 能解释候选在哪一级消失；
3. 最高置信结果颜色和标签与实物一致；
4. 四点均为有限值，顺序为 LT、RT、RB、LB，构成正面积凸四边形；
5. 四点落在目标附近，而不是只得到一个看似正确的类别；
6. 连续运行时识别订阅者的 `dropped` 可以增加，但队列和延迟不能持续增长；
7. 关闭程序时 CUDA stream、context、device/host buffer 和 engine 都在 vision 线程退出后释放。

P1 至少在近、中、远三种尺寸和红蓝各一种画面上人工核对。若现场只有单方装甲，另一颜色明确记为待验证，不能写成已通过。

### 6.4 P2 同帧叠加

获得结果话题文件授权并实施后，通过条件为：

- display 显示的图像时间戳与 detection 消息相同；
- 四边形紧贴装甲板，移动相机时没有明显套到上一帧；
- 标签文字包含颜色、编号和 objectness；
- 关闭显示只停止 clone/绘制，不停止模型推理；
- 窗口创建、`imshow`、`waitKey`、销毁仍全部在主线程。

### 6.5 性能只记录，不先承诺

第一轮必须记录：

```text
camera fps / vision fps / subscriber dropped
preprocess P50/P95
inference P50/P95
postprocess P50/P95
capture timestamp 到结果产生的帧龄 P50/P95
GPU 显存稳定值
```

在真实测量前不写“必达30 FPS”。如果同步模型推理已经低于相机30 FPS，先保留最新帧丢弃语义；只有模型结果正确且性能确实不足，才进入异步请求池或动态 ROI，不能在正确性尚未确认前增加并发复杂度。

## 7. 失败时怎么定位

| 现象 | 先检查 | 禁止做法 |
| --- | --- | --- |
| ONNX 无法生成 engine | TensorRT/CUDA版本、ONNX解析错误原文 | 换备用模型后声称0526已接入 |
| engine 无法反序列化 | 是否由当前GPU/当前TensorRT生成 | 从别的机器复制 engine 硬跑 |
| `raw_rows/cols` 不等于 `25200/22` | engine张量与构建命令 | 修改解析器迁就错误输出 |
| `max_objectness` 全部很低 | RGB、`/255`、NCHW、左上填充 | 先把0.8阈值降到很低 |
| 候选多但颜色整体相反 | 0526颜色顺序是否为 blue/red/gray/purple | 直接交换枚举值污染全工程 |
| 标签整体错位 | 9路显式映射，尤其0/1/7/8 | 用 `static_cast<ArmorLabel>(id)` |
| 框正确但四点顺序交叉 | 是否按 `[p0,p3,p2,p1]` 重排 | 按坐标重新猜点序 |
| vision FPS低但延迟不增长 | 这是单槽丢旧帧的预期行为 | 加无界队列保住每一帧 |
| 模型粗四点不够准 | 先保存模型直出事实，再评估P3 | 让精修失败删除YOLO目标 |

如果默认 `0.8` 下完全没有目标，但预处理和 engine 契约都已确认，结论只能是“现有模型在当前画面/曝光/目标域上未验证或不适用”。必须先保留这个真实结论，再由用户决定是否调曝光、测试参考 demo、调整阈值或更换模型；实现者不得自行重新训练。

## 8. 实施顺序与停止点

```text
用户授权安装推理依赖
→ P0 安装并验证 CUDA Toolkit / TensorRT
→ 用户确认允许生成 build/0526.engine
→ P0 engine 契约通过
→ P1 只修改现有8个文件
→ vision日志证明真实相机识别打通
→ 用户明确授权 vision_to 文件
→ P2 同帧可视化
→ 模型直出稳定后，按需决定是否进入 P3 精修
```

每个箭头都是停止点。前一项没有真实证据时不进入后一项，不把编译通过、engine 加载成功、出现一个候选或窗口里偶尔框到目标混写成“装甲板识别完成”。

## 9. 本规划完成定义

本文只负责把快速接入路线写清楚，不代表运行时已经实现。规划通过应满足：

- 唯一模型、唯一后端和当前环境缺口明确；
- 预处理、22列输出、点序、颜色、标签、尺寸、阈值和NMS全部对应参考源码；
- 每个现有文件改什么、为什么改、如何验收写清楚；
- 新文件、新目录、依赖安装、engine 生成均设置单独授权点；
- 模型直出、可视化、精修分阶段，不再被传统灯条/数字分类旧路线拖住；
- 没有把未运行、未测精度和未测性能写成完成事实。
