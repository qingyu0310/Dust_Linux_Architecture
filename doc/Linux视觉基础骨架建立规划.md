# Linux 视觉基础骨架建立规划

日期：2026-10-12

## 1. 目标与范围

沿用 Dust/Zephyr 子树的六层职责，在嵌入式 Linux 用户空间建立原生 C++ 视觉工程。使用 CMake 构建普通 Linux 可执行程序，由操作系统管理进程，不使用 ROS2、ament、colcon、ROS 消息或 launch。

本文件是实施规划。第一阶段交付可编译、可运行、可正常退出的基础骨架，以及最小相机采集和图像处理链路。装甲板识别、神经网络推理、PnP、自瞄和真实电控协议留到后续阶段。

## 2. 执行模型：先建立一个 Linux 进程

基础程序命名为 `vision_app`，运行方式为：

```bash
dust run
```

一个进程内装配相机、处理流水线、调试输出和生命周期管理。六个框架目录是代码职责划分，不对应六个进程。

基础版本通过 `REGISTER_THREAD` 注册一个视觉业务线程，在线程内完成“采集一帧 → 处理一帧 → 输出结果”。主线程负责统一启动、等待停止和统一退出。后续需要并行时，再注册独立采集线程和处理线程，使用有界队列连接。注册宏本身不创建进程。

多进程适用于需要单独重启、故障隔离或独立部署的组件。基础阶段不引入共享内存、Unix socket 或跨进程消息总线。将来确有需要时，由独立适配实现跨进程传输，保留既有数据契约。

## 4. 六层职责与依赖

| 层 | 负责内容 | 边界 |
|---|---|---|
| algorithm | 图像处理、几何、滤波等可复用计算 | 不访问设备，不管理进程，不依赖项目配置 |
| drivers | 打开设备、配置采集、读取帧、关闭设备 | 不识别目标，不做业务决策 |
| modules | 组合驱动和算法，维护设备状态及处理流水线 | 不承担整机业务装配 |
| topic | 定义帧与结果的数据结构 | 不访问设备，不执行识别流程 |
| cmd | 日志、调试与通用 YAML 读取类 | 不持有整机控制策略 |
| init | 注册表、阶段启动、线程管理、退出信号和生命周期 | 不直接写相机和识别业务 |
| project | 配置具体模块、组织处理顺序和业务输出 | 通过模块接口使用框架能力 |

依赖约束：

```text
algorithm、topic：基础数据与计算
drivers：依赖设备库，按需使用 topic 数据类型
modules：依赖 drivers、algorithm、topic
cmd：提供公共日志、调试和 YAML 读取能力
init：提供生命周期和信号基础设施
project：组合以上能力，在所属源文件注册初始化与业务线程
```

所有框架层不得反向包含 `project`。公共日志可被其他层调用，但日志实现不得反向依赖业务模块。

纯计算允许依赖 OpenCV、Eigen 等算法库。“纯计算”表示没有设备与运行管理副作用，并不要求只能使用标准库。

## 5. 与 Zephyr 子树的对应

| Zephyr 机制 | Linux 基础骨架中的实现 |
|---|---|
| Kconfig 功能裁剪 | CMake 选项与显式目标依赖 |
| DTS/板卡配置 | 运行配置中的设备路径、相机参数 |
| REGISTER_INIT | 保留宏注册，收集初始化函数，按阶段及 High → Mid → Low 执行 |
| REGISTER_THREAD | 保留线程启动函数注册，底层使用 std::thread 或 pthread |
| System_Startup | 保留统一入口，遍历初始化与线程注册表 |
| zbus/消息队列 | 同进程数据结构；并发阶段引入有界队列 |
| Zephyr 外设封装 | Linux 相机、串口、SocketCAN 等设备封装 |
| Shell、DUST_LOG | 终端调试命令与日志 |

第一阶段保留 Dust 的注册式启动架构。`REGISTER_INIT`、`REGISTER_THREAD` 和 `System_Startup()` 是自定义 C/C++ 机制，可以在 Linux 用户空间实现。

使用 GCC section 属性和 GNU ELF 链接脚本收集 `.user_init`、`.user_thread` 注册项，提供 start/end 边界符号。初始化阶段沿用 `PreInit → EarlyInit → MidInit → LateInit → AppInit`，对应阶段初始化完成后，再执行相应线程启动注册项。

注册项由拥有资源的模块或项目源文件定义，启动器只遍历注册表，不维护相机、检测器等具体业务列表。初始化阶段、初始化等级和失败策略分别表达；同阶段按 High → Mid → Low 执行，同等级允许多项，按链接表遍历。线程项只按阶段遍历；有先后依赖的组件应使用现有阶段和等级表达，不依赖同等级的链接顺序。

补充 Linux 生命周期：线程必须支持停止请求和等待退出；成功初始化的资源登记清理动作，在正常退出或启动失败时按依赖逆序释放。关键初始化失败时停止继续启动，清理已启动线程和资源后返回非零退出码。

## 6. 最小类型与接口

### 6.1 图像帧契约

`ImageFrame` 至少包含：

- 帧序号。
- 主机单调时钟时间戳，并明确它是采集完成时间，不能冒充硬件曝光时间。
- 图像数据及像素格式约定。
- 设备标识。

基础实现可以使用 `cv::Mat` 表达图像，明确 BGR、GRAY 等格式。跨阶段共享时约定发布后只读；需要原地修改的处理步骤必须取得独占数据或显式复制。`cv::Mat` 的浅拷贝不会自动解决并发写问题。

### 6.2 相机驱动

`CameraDriver` 提供打开、读取和关闭接口。基础后端使用 OpenCV `VideoCapture`，在 Linux 上选择 V4L2 后端。后续可增加工业相机 SDK 后端。

读帧接口区分成功、超时和设备错误。实际后端必须验证阻塞行为，确保停止请求后能在有限时间内退出；不能只设置一个停止标志就声称阻塞读操作可被中断。

### 6.3 相机模块

`CameraModule` 包装驱动，负责配置校验、帧序号、时间戳和状态。基础版本不拥有独立线程，由注册的视觉业务线程调用。

### 6.4 视觉模块

`VisionPipeline` 接收一帧，调用算法并返回 `VisionResult`。第一阶段沿用灰度、模糊、二值化和轮廓处理，只验证链路，不赋予轮廓“已识别目标”的语义。

结果保留输入帧序号和时间戳，便于后续判断结果年龄、定位延迟。调试图像与业务结果分开表达。

### 6.5 项目应用

`项目业务线程` 负责组合模块，并在所属源文件通过 `REGISTER_INIT` 注册资源初始化，通过 `REGISTER_THREAD` 注册业务线程启动函数。运行循环留在项目业务线程中。每个线程在所属目录保存 YAML，并在自己的初始化注册项中读取、校验，只向对应模块传递已解析参数。模块初始化失败时，已创建的资源必须通过 RAII 和统一清理流程释放。

`main.cpp` 仅调用统一启动、等待和关闭接口，不放图像处理代码或逐个模块启动调用。

## 7. 启动、运行与退出

```text
main
  → System_Startup()
      → 建立退出信号处理
      → 遍历各阶段 .user_init 注册项，所属线程读取自己的 YAML
      → 执行对应阶段 .user_thread 启动函数
  → System_WaitForStop()
      → 等待退出信号或业务线程报告错误
  → System_Shutdown()
      → 通知所有线程停止，解除阻塞
      → 等待线程退出，逆序释放已初始化资源
  → 返回退出码
```

统一入口形式：

```cpp
int main()
{
    if (System_Startup())
    {
        System_WaitForStop();
    }
    return System_Shutdown();
}
```

上述代码表达规划接口。关闭函数应可重复调用，并保存启动或运行错误对应的退出状态。线程启动注册函数只负责启动并返回，不能直接执行永久业务循环，否则会阻塞后续阶段。

支持 `SIGINT` 和 `SIGTERM`。基础信号处理函数只设置 `volatile sig_atomic_t` 停止标志，不在信号处理函数中输出日志、加锁或释放设备。主线程等待循环观察标志后，将停止请求传递给业务线程并执行正常清理。

所有通过注册项启动的线程均纳入统一管理：先通知停止，再解除阻塞、等待线程退出，最后释放其访问的资源。禁止以 detached 线程代替生命周期管理。

正常退出返回 0；配置错误、设备初始化失败和无法恢复的运行错误返回非零。基础阶段明确报错退出，不加入未经验证的自动重连机制。

## 8. 每线程 YAML 与调试

每个业务线程子目录自带 YAML，线程参数结构、字段名和允许范围留在对应线程源文件；读取和通用校验由 `cmd::config::Config` 类封装，不建立总配置文件、集中参数结构或全局命令行配置入口。

当前已实现的 test 线程示例：

```text
project/thread/test/
├── CMakeLists.txt
├── trd_test.cpp
└── trd_test.yaml
```

```yaml
heartbeat_ms: 1000
run_duration_ms: 0
```

对应 `thread_init()` 使用局部 `cmd::config::Config` 对象，通过 `Load()` 加载本线程 YAML，通过 `GetInt()` 提取参数。类内部使用 yaml-cpp，拒绝缺失字段、重复字段、未知字段、无效类型和越界数值。初始化失败报告错误，并进入统一清理流程。

由 `project/thread/CMakeLists.txt` 统一装配各线程源码，并将各线程 YAML 复制到可执行文件旁的 `thread/<功能>/`。线程子目录不单独设置 CMakeLists。运行时按可执行文件位置读取，启动工作目录不会影响路径。参数只在初始化时读取，修改后重启生效；部署时保留线程 YAML 的相对目录结构。

新增线程按同样方式在自己的子目录装配源码和参数；不为尚未实现的线程创建空配置文件。相机模块暂不实现，后续相机相关参数也由所属业务线程 YAML 提供。

终端调试和 DUST_LOG 保持独立，YAML 不承担日志命令分发或公共启动管理。

## 9. 构建规划

根目录提供原生 CMake 入口，使用 C++17，按实际模块建立库目标。保留 Eigen 算法依赖，相机与图像处理目标链接 OpenCV。基础程序不链接 MuJoCo。线程目标通过 `find_package(Threads REQUIRED)` 链接 `Threads::Threads`。

```bash
dust build       # 增量编译
dust build -p    # 清空 build 后全量编译
dust run         # 运行基础进程
```

命令入口位于 `framework/cmd/build`，由 `.vscode/settings.json` 仅向本工作区新建的集成终端 PATH 添加脚本目录，不做全局安装。命令从当前目录向上定位工程根，支持根目录和子目录执行。底层使用原生 CMake，默认 Debug，产物保存在根目录 `build`。`dust run` 直接接管程序进程，保留终端输入、信号和退出码；终端使用方式见根 README。

注册机制的构建要求：

- 使用补充链接脚本保留 Linux 默认链接布局，通过 `KEEP()` 保留注册段，并定义遍历边界符号。
- 注册项结构、段布局和对齐须与遍历方式一致，不能假定存在属性就能安全连续遍历。
- `used` 属性防止编译器省略注册项；它不能保证静态库中未引用的对象文件被链接器抽取。注册源文件优先通过 CMake OBJECT library 或直接源文件加入可执行程序；若采用静态库，则对必要注册库定向使用 whole-archive。
- 优化构建及启用 section 回收时，仍须验证注册项完整；用链接 map、`readelf` 或 `nm` 检查段与边界符号，并用运行日志确认阶段执行。

真实 `compile_commands.json` 位于构建目录，由编辑器使用该文件。`temp` 不通过递归扫描进入构建。

嵌入式部署后续通过 CMake toolchain 支持交叉编译，并核对目标端 OpenCV、标准库和动态库依赖。第一阶段先在当前 Linux 主机建立可运行基线。

## 10. 现有工程迁移步骤

1. 保存可恢复的现有源码基线。
2. 新建根 CMake 和六层目录，保留已有纯计算代码。
3. 将相机设备访问提取到 drivers，将处理计算提取到 algorithm，再由 modules 组合。
4. 建立 Linux 注册项、链接脚本、线程封装及 `System_Startup/WaitForStop/Shutdown`，验证阶段启动与退出。
5. 建立 `ImageFrame`、`VisionResult` 和 `项目业务线程`，注册初始化及业务线程，将唯一入口放在 `framework/init/main.cpp`。
6. 用原生 CMake 替换现有 ament 构建，移除 ROS2 发布、节点继承与 spin 调用。
7. 移除不再使用的 ROS2 package 清单和相机 launch，更新编辑器构建数据库配置。
8. 整理现有仿真和键盘代码：将需要保留的参考内容归档到 `temp`，活动骨架中不残留 ROS2 入口和依赖。MuJoCo 后续按独立可选能力接入。
9. 验证基础进程和相机处理链路，记录实际结果及待验证项。

上述步骤为迁移路线；当前实施范围见文末“基础骨架实施状态”。

## 11. 第一阶段验收

| 验收项 | 所需证据 |
|---|---|
| 独立构建 | 未加载 ROS2 环境时，原生 CMake 配置与编译通过 |
| 独立运行 | `vision_app` 是普通 Linux 进程，无 ROS2 运行依赖 |
| 最小处理链路 | 实际图像进入模块并产生关联帧序号的处理结果 |
| 无桌面运行 | 关闭显示后无需图形会话即可处理图像 |
| 失败路径 | 错误配置、无效设备路径能够输出原因并非零退出 |
| 注册式启动 | 注册段、边界符号完整，阶段与 High → Mid → Low 执行顺序符合定义 |
| 启动回滚 | 初始化或线程启动失败后，已启动线程退出、资源释放，返回非零 |
| 正常停止 | 采集运行中发送 SIGINT、SIGTERM，实测退出延迟和资源释放 |
| 边界清晰 | 框架不包含 project，入口不包含识别算法实现 |

编译成功只证明构建成立。相机访问、无桌面运行和退出时延必须实测；没有相机时可用离线图像或视频验证计算链路，但真实设备链路仍标记待验证。

### DUST_LOG 对齐状态

日志按参考子树放在 `framework/cmd/shell`，保持 `debug::Log`、`DUST_LOG_INF/ERR/OK/WRN/DBG` 和命名 DBG 单选语义，移除先前自创的等级过滤接口及 `log.level` 配置。

通道策略、DBG 注册表、记录、优先级帧队列和终端发送后端分别组织。调试台在所属文件注册 PreInit/PreThread 项，读取 stdin 的 `log list/on/off/mode`，向 stderr 输出。

Linux 差异：调用点用 `vsnprintf` 生成自有文本，队列不保存 32 位参数槽或调用方指针；终端替代 UART/DMA，重定向输出关闭 ANSI 颜色。队列满且不能挤出低优先级帧时，事件与命令触发同步排空，DBG 可丢弃，因此不是硬实时日志后端。没有移植调试变量或 UART 驱动。

终端交互已补齐输入与日志协调：同一终端中由 shell 逐字编辑命令，日志后恢复提示符、当前输入及光标，关闭时恢复终端属性。平台启动明确忽略 SIGPIPE，写失败后经统一停止流程退出；正式测试覆盖运行期断管清理和持续日志期间的终端输入。文件、管道或不支持重绘的终端保留原输入方式，不输出输入提示符及重绘序列。
