# HikRobot 断线重连与 Thread 异常恢复 Hook 规划

## 1. 当前实现与本次规划

原实现由相机 Task 内捕获异常并重连；现已改为 Thread 公共入口调用项目层恢复 hook。

本次实现将异常恢复入口放到 `init::Thread` 的公共线程入口，由业务注册恢复 hook。相机任务只负责正常采集，恢复 hook 负责重连，线程框架负责判断是否重新执行任务。

**已实现 Thread 可选恢复 hook，相机通过 `SetRecoveryHook(Recover)` 注册。**

## 2. Thread 增加可选恢复 Hook

实际恢复结果枚举：

```cpp
enum class RecoveryAction
{
    Restart,    // 恢复成功，重新执行任务入口
    Stop        // 无法恢复，请求统一退出
};
```

实际回调接收异常、线程对象和业务上下文：

```cpp
using RecoveryHook = RecoveryAction (*)(
    const std::exception& error,
    Thread& thread,
    void* context);

void SetRecoveryHook(RecoveryHook hook, void* context = nullptr);
```

注册必须在 `Start()` 前完成，不允许工作线程运行期间修改回调或上下文。上下文由调用方持有，生命周期必须覆盖线程执行及 `Join()`。

不注册 hook 的线程保持现有行为：任务异常时报告错误并请求统一退出。框架不识别 SDK，也不内置相机重连配置。

## 3. 公共线程入口执行规则

```text
设置线程名
    ↓
执行 Task
    ├─ 正常返回 → 工作线程结束
    └─ 抛出 std::exception
         ├─ 收到停止请求 → 工作线程结束
         ├─ 没有恢复 hook → 报告异常并请求统一退出
         └─ 调用业务恢复 hook
              ├─ 收到停止请求 → 工作线程结束
              ├─ 返回 Restart → 重新执行 Task
              ├─ 返回 Stop → 报告异常并请求统一退出
              └─ hook 抛出异常 → 报告恢复失败并请求统一退出
```

非 `std::exception` 异常继续采用现有统一退出流程，不交给上述类型的 hook。线程名设置等框架启动错误也不进入业务恢复流程。

公共入口使用循环重新调用任务，不递归调用 `Run()`，也不在 hook 内调用 `Start()` 创建另一条线程。

### 重新执行不等于继续原调用栈

Task 抛出异常后，原来的任务调用栈已经展开，局部资源按正常 C++ 析构规则释放。恢复成功只能重新进入 Task，无法从原来的出错语句继续执行。

因此任务必须允许重新进入，局部统计和时间基准会重新初始化；静态成员和业务对象不会自动重置，必须由业务 hook 处理。

### 停止与异常的优先级

停止请求优先于恢复和重启。框架在调用 hook 前以及 hook 返回后都检查 `StopRequested()`，避免退出过程中重新开始任务。

业务 hook 使用 `WaitForStop()` 等待，收到停止请求后返回即可；框架检测到停止状态时直接结束线程，不把正常停止当成恢复失败。

框架无法立即中断已经执行中的 SDK 调用。退出耗时仍可能包含 SDK 打开、关闭或取帧操作的耗时。

## 4. 相机业务怎样接入

### Task：只负责正常采集

保留以下职责：

- 调用同步 `camera_.Read()` 获取图像。
- 向主线程提交最新帧。
- 输出首帧信息和帧率统计。
- 检查停止请求。
- 单次无数据继续读取，连续无帧达到 `max_frame_gap_ms` 时抛出异常。

移除 Task 内部的重连捕获分支，让可恢复异常传到公共线程入口。

### 相机恢复 Hook：判断故障并重新打开设备

1. 根据异常类别判断是否可以恢复。设备离线、取帧故障及连续无帧可以进入重连。
2. 配置错误、逻辑错误和内存分配失败等返回 `Stop`，避免无限重试掩盖程序错误。
3. 在原采集线程中调用 `camera_.Stop()`，关闭旧设备并释放旧 SDK 引用。
4. 在帧互斥锁保护下清空尚未显示的最新帧。
5. 使用 `WaitForStop(1000 ms)` 等待，停止请求可以唤醒等待。
6. 使用原有配置重新调用 `camera_.Init()`，枚举、匹配设备并重新设置曝光、增益和帧率。
7. 暂时未找到设备或设备尚未恢复时，记录失败原因，等待后继续尝试。
8. 初始化成功后返回 `Restart`，框架重新进入 Task，采集统计和无帧计时自然重置。

重连成功应只表示初始化及开始采集成功；是否确实恢复有效图像，由重新进入 Task 后的首帧结果确认。

### 异常分类需要明确设计

模块现提供 `HikRobotError`，继承 `std::runtime_error`，通过 `GetCode()` 保留 SDK 错误码，通过 `IsRecoverable()` 标记可恢复故障。错误消息保留操作名称。

当前允许重试的 SDK 错误为设备离线、设备无响应、USB 读写错误、USB 设备异常、无数据和异常图像。未找到匹配设备、模块检测到的无效或不完整图像，以及项目层连续无帧也使用可恢复 `HikRobotError`。其他 SDK 错误默认不可恢复，未知 USB 错误不会盲目重试。

恢复 hook 仅接受标记可恢复的 `HikRobotError`，其他异常返回 Stop。旧设备清理失败或初始化回滚失败均终止恢复并请求统一退出；不会把本地状态清空当成 SDK 资源释放成功。

## 5. 模块、线程与显示的责任

| 层级 | 职责 |
| --- | --- |
| `framework/modules/camera` | SDK 调用、设备资源、同步取帧、明确的故障信息 |
| `framework/init/thread.hpp` | 捕获任务异常、调用可选恢复 hook、判断停止与重新执行 |
| `project/thread/camera` | 无帧时限、故障恢复策略、重连等待、重新初始化设备 |
| 主线程显示回调 | OpenCV 窗口创建、图像显示和窗口事件处理 |

所有读帧、关闭和重新初始化操作均在同一工作线程内串行执行。最终退出时仍先请求停止、等待线程结束，再执行资源释放入口。

这个 hook 在原工作线程执行，不新增守护线程。它只处理任务抛出的异常，不能发现一个永久阻塞、无法抛异常的任务；线程卡死监测属于另一项设计。

## 6. 与当前 Task 内重连方案比较

| 比较项 | 当前 Task 内重连 | Thread 恢复 Hook |
| --- | --- | --- |
| 改动范围 | 仅相机业务 | 公共线程框架和相机业务 |
| 采集循环 | 包含异常捕获和恢复分支 | 集中于正常采集，异常传到框架 |
| 恢复后执行 | 在当前 Task 调用内继续循环 | 重新执行 Task，局部状态重新初始化 |
| 恢复策略归属 | 相机业务 | 仍由相机业务 hook 决定 |
| 多设备接入 | 每个任务自行组织捕获流程 | 复用异常恢复入口，各设备注册自己的 hook |
| 框架复杂度 | 较低 | 增加回调注册、停止优先级和二次异常处理 |
| 未接入的线程 | 不受影响 | 必须保持原有异常退出行为 |
| 卡死检测 | 不支持 | 同样不支持 |
| 真实恢复能力 | 取决于重连代码及设备状态 | 同样取决于业务恢复代码及设备状态 |

只接一个相机时，当前方案更简单。对于后续会接入串口、网络及其他设备的 Dust 架构，可选恢复 hook 更适合统一组织异常入口。

**建议采用 Thread 可选异常恢复 hook，设备恢复策略留在项目层。** 好处是统一线程生命周期和异常分发；并不会因为加入 hook 就自动提高设备恢复成功率。

## 7. 本次实施内容

1. 在 `Thread` 增加恢复结果、hook 类型和启动前注册接口。
2. 改造公共任务入口，支持恢复后循环重新执行，保留未注册 hook 的默认异常退出行为。
3. 明确相机可恢复异常类别，避免捕获所有运行时错误后无条件重试。
4. 将项目层 `Reconnect()` 调整为相机恢复 hook，移除 Task 内重连分支。
5. 保持 YAML 的 `max_frame_gap_ms` 作为重连触发时限，初版沿用 1 秒重试等待，不新增配置项。
6. 更新相机说明文档中关于异常恢复和退出的描述。

启动阶段仍保留现有严格初始化：首次启动找不到相机时按初始化规则报错。公共任务 hook 不会自动接管 `thread_init()` 的异常；若需要启动时等待设备，应另行明确该行为。

## 8. 验证计划

公共线程框架需要验证：

- 未注册 hook 的任务异常仍请求统一退出。
- hook 返回 `Restart` 后确实重新执行入口，任务局部状态重新初始化。
- hook 返回 `Stop` 或自身抛异常时结束恢复并请求统一退出。
- hook 等待期间收到停止请求可以退出，且不重新执行任务。
- 正常返回的任务不会被自动重启。

相机实际运行需要验证：

- 拔线后进入恢复，其他线程和主线程窗口事件仍能运行。
- 重插后重新枚举并恢复有效图像，曝光、增益和帧率配置重新应用。
- USB 节点变化后仍能匹配相机；访问权限必须由系统保证，重连不会自行修改权限。
- 相机长期缺失时等待不空转，日志按重试周期输出。
- 在重连等待以及重连成功附近请求退出，不发生重复启动或资源并发访问。

本次 hook 实现已通过 `cmake --build build -j 4` 编译。公共线程独立测试通过：未注册 hook 的异常退出、恢复后重新执行、拒绝恢复、hook 自身异常、等待期间停止、正常返回不重启，以及运行时拒绝修改 hook。测试隔离了系统退出和日志输出，验证的是线程控制流程。实际硬件拔插恢复仍待验证。

## 9. 运行时调参与重连

曝光和增益由 shell 通知版 var 同步提交到单请求槽，相机 Task 在每轮取帧前消费通知并调用 SDK。运行期 SDK 只由相机工作线程访问，不再由 shell 与采集线程共享设备二值信号量。

通知型 var 在释放参数锁后等待相机 Task 的实际设置结果，SDK 成功后才提交显示值和类内成功配置。重连调用 `Reopen()` 使用最近成功配置。进入恢复时取消尚未执行的调参请求，设备离线期间拒绝新请求；失败请求不在重连后自动补写。

2026-10-13 已实测连续采集期间曝光和增益设置，以及参数提交期间 SIGTERM 正常退出。调参过程中拔线和重连后的再次调参仍待实机专项验证。

详情见 [运行时调参](HikRobot相机模块与SDK接口说明.md)。
